# Skill 评审检查清单（裁判师版）

> 52 项检查点，10 大维度。每项含「编号 / 检查内容 / 优先级 / 对应工作流」四元组。
> 评审时由 W2 与 W3 共同消费本表：命中即落优点（W2 视角）或落问题（W3 视角）。

## 三段式评审元框架（W2/W3 扫描前置）

> 清单式扫描只能发现"格式与结构缺陷"，发现不了"方向错误的技能"——一个 frontmatter 合规、行数达标、路由清晰的过程式 Skill，可能在第一性层面就是错的（指导 AI 怎么做而非结果导向）。因此 W2/W3 在逐项扫描本表**之前**，必须先完成三段式思维：

1. **第一性锚定（先于一切扫描）**：回答三问——① 这个 Skill 的第一性问题是什么（用户/系统真正缺什么，而非它当前在做什么）？② 不可违背约束是什么（非破坏契约、安全性、平台物理现实，排序列出）？③ 边界在哪（什么不是它的活）？落成一句话锚定：「该 Skill 必须 ___，绝不 ___，不管 ___（借来的/不适配的手段）」。锚定结论写入报告第 2 段「第一性结论」。
2. **双向钢人论证（对关键设计选择）**：对锚定后发现的可疑设计选择（如从其他场景借来的模式、与第一性约束冲突的手段），构建最强 FOR 与最强 AGAINST，提炼核心分歧后给出方向判断（对/错）。仅对可疑选择做，不做全文钢人。结论落入报告第 5 段对应问题的「建议」字段，或第 3 段优点（钢人后确认的设计）。
3. **对抗式审查（D 系列检查项）**：本表 D1-D4 是对抗式审查的固化——以"审查者试图攻破它"的视角逐项检查四类高频坑。这是清单的一部分，随 W3 正常扫描执行。

> 执行顺序：锚定 → 可疑点钢人 → 逐项清单扫描（含 D 系列）。锚定发现方向性错误时（如第一性问题与实际产出错位），无论清单命中多少项，必须在报告第 2 段显式给出「方向判断：错位」结论，此时清单问题降为次要。

## 字段归属说明

### 官方规范字段（specs/spec.md）

| 字段            | 必需 | 类型 / 约束                                      |
| --------------- | ---- | ------------------------------------------------- |
| `name`          | 是   | 1-64 字符，小写字母+数字+连字符，须匹配目录名    |
| `description`   | 是   | 1-1024 字符，须描述"做什么"+"何时用"              |
| `license`       | 否   | 许可证名称或文件引用                              |
| `compatibility` | 否   | 1-500 字符，环境要求（Python 版本、系统依赖等）   |
| `metadata`      | 否   | string→string 映射，value 必须为字符串            |
| `allowed-tools` | 否   | 空格分隔单字符串（非 array），实验性字段          |

### 项目扩展字段（放入 metadata 内部）

| 字段      | 说明     |
| --------- | -------- |
| `tags`    | 标签列表 |
| `origin`  | 技能来源 |
| `repo`    | 仓库地址 |
| `updated` | 更新时间 |

> **注意**：`triggers` 不是官方字段，触发信息应直接写入 `description` 中。

> **项目扩展字段使用原则**：项目扩展字段（tags、origin、repo、updated）不是官方规范硬限字段，评审时不应作为合规要求或 P0/P1 问题提出。优化实施时，除非用户明确指令要求添加，否则不主动加入这些字段。O1a 检查项应降级为信息性提示而非整改要求。

### B3 触发条件说明

- 官方规范中 `description` 是主要触发机制，无独立 `triggers` 字段
- 评审时应检查：
  1. `description` 是否同时描述「做什么」与「何时使用」（官方要求）
  2. `description` 是否包含帮助 Agent 识别相关任务的关键词
  3. `description` 是否声明不处理的边界场景（最佳实践，非官方硬限）

> **注意**：官方 `spec.md` 仅定义 6 个 frontmatter 字段（name, description, license, compatibility, metadata, allowed-tools）。`triggers` 不是官方字段，评审时不应将其作为合规要求。`allowed-tools` 类型为空格分隔单字符串（非 array）。

## 编号体系

检查项编号由**维度前缀 + 序号**组成，维度前缀对应 9 大维度：

| 前缀 | 维度               | 编号范围 | 说明                     |
| ---- | ------------------ | -------- | ------------------------ |
| O    | 起源 (Origin)      | O1-O3    | 真实任务提炼与迭代       |
| S    | 结构 (Structure)   | S1-S6    | 文档职责与 frontmatter   |
| C    | 上下文预算 (Context)| C1-C4   | 内聚与下沉               |
| I    | 实现 (Implementation)| I1-I3  | 脚本入口与产物路径       |
| T    | 触发与意图 (Trigger)| T1-T5   | description 语义（W7 唯一判定）|
| M    | 模式与深度 (Patterns)| M1-M7  | Gotchas / P-V-H / 验证闭环|
| P    | 脚本设计 (Scripts) | P1-P7    | CLI 规范与输出           |
| V    | 验证闭环 (Verification)| V1-V7 | 数据判定与术语一致性     |
| B    | 边界 (Boundary)    | B1-B4    | 运行时要求与非目标       |
| D    | 设计对抗 (Adversity)| D1-D4   | 对抗式审查四类高频坑（三段式元框架固化）|

**编号引用规则**：
- W5 整改方向必须标注 W3 命中项编号（如 `命中：S1、P3`），否则断链
- W7 审计结果回写 W3 时标注 T 系列编号（如 `T2 未命中`）
- 新增检查项时，在对应维度末尾追加序号（如 P8），不插入中间

## 检查项总表

| 编号 | 检查内容                                       | 优先级 | 对应工作流 |

| O1a  | metadata 是否包含 `origin` 字段                | P2     | W3         |
| O1b  | changelog 是否独立为 VERSION.md（非内嵌）      | P2     | W3         |
| O2   | 是否经过至少一轮 execute-then-revise 迭代      | P2     | W2 / W3    |
| O3   | 是否阅读过执行轨迹 (Trace) 识别 Agent 试错信号 | P2     | W2 / W3    |

| 编号 | 检查内容                                          | 优先级 | 对应工作流      |
| ---- | ------------------------------------------------- | ------ | --------------- |
| S1   | 主文档是否只承担路由职责（不装大段代码 / 知识）   | P0     | W2 / W3         |
| S2   | 主文档是否使用结构化标记（H2 / 列表 / Checklist） | P0     | W3              |

| S6   | Frontmatter 字段是否过度工程化 + compatibility ≤500 字符 + metadata value 为 string + 版本三处一致性 | P1     | V0（硬限） / W3 |

| 编号 | 检查内容                                     | 优先级 | 对应工作流          |

> **T 系列归属说明**：W3 不直接判 T 系列，统一委托给 W7 深度审计，W7 输出回写 W3 的 P1 子项。

### M 模式与深度 (Advanced Patterns)

| 编号 | 检查内容                                      | 优先级 | 对应工作流 |
| ---- | --------------------------------------------- | ------ | ---------- |
| M1   | 是否有 Gotchas 段且条目是具体纠正             | P0     | W2 / W3    |
| M2   | 输出格式是否有模板而非散文描述                | P1     | W2 / W3    |
| M3   | 多步工作流是否有显式 Checklist                | P1     | W3         |
| M4   | 是否有 Validation Loop 让 Agent 自检          | P1     | W2 / W3    |
| M5   | 破坏性操作是否采用 Plan-Validate-Handoff 模式 | P1     | W2 / W3    |
| M6   | 做法优于答案：是否教方法论而非死指令          | P2     | W2 / W3    |
| M7   | 解释 Why：关键指令是否有逻辑支撑而非单纯 MUST | P2     | W2 / W3    |

### P 脚本设计 (Agentic Scripts)

| 编号 | 检查内容                                           | 优先级 | 对应工作流 |
| ---- | -------------------------------------------------- | ------ | ---------- |
| P1   | 一次性命令是否固定版本 (npx tool@version)          | P2     | W3         |
| P2   | 脚本是否声明内联依赖 (PEP 723 / npm:)              | P1     | W3         |
| P3   | 严禁交互：是否完全无 input() / TTY 阻塞            | P0     | W3         |
| P4   | 是否实现 --help 且简洁自描述                       | P1     | W3         |
| P5   | 错误信息是否可操作（出错处 + 预期 + 建议）         | P1     | W3         |
| P6   | 是否结构化输出且分离 stdout / stderr               | P1     | W3         |
| P7   | 是否考虑输出截断（默认摘要 / --offset / --output） | P2     | W3         |

### V 验证闭环 (Verification)

| 编号 | 检查内容                                          | 优先级 | 对应工作流 |
| ---- | ------------------------------------------------- | ------ | ---------- |
| V1   | 数据获取 / 处理是否有成功判定标准                 | P1     | W3         |
| V2   | 数据对象是否有字段完整性检查                      | P1     | W3         |
| V3   | 最终产物是否有落地检查                            | P1     | W3         |
| V4   | 是否有评估测试集（正面集 + 负面集）用于回归验证   | P2     | W3         |
| V5   | 评估断言是否可机器判定（非主观评分）              | P2     | W3         |
| V6   | 评审报告 W5 每条建议是否包含 checklist 编号标注   | P1     | W3         |
| V7   | 术语一致性：是否运行 --consistency 检查旧术语残留 | P2     | W3         |

### B 边界 (Boundary)

| 编号 | 检查内容                                               | 优先级 | 对应工作流 |
| ---- | ------------------------------------------------------ | ------ | ---------- |
| B1   | 是否声明运行时要求 (Python 版本、系统依赖)             | P2     | W3         |
| B2   | 非执行性材料（复盘 / 故事）是否被显式标注              | P2     | W3         |
| B3   | 触发条件是否清晰可判定，description 是否包含触发关键词 | P0     | W3         |
| B4   | 非目标 (Non-Goals) 是否被显式列出                      | P2     | W3         |

### D 设计对抗 (Adversity)

> 对抗式审查固化维度（源自第一性原理 + 对抗推导）。以"审查者试图攻破该 Skill"的视角逐项检查，四类坑均为实战中反复出现的高频缺陷。

| 编号 | 检查内容                                                       | 优先级 | 对应工作流 |
| ---- | -------------------------------------------------------------- | ------ | ---------- |
| D1   | 非破坏约束是否被强制：核心安全承诺（不破坏用户产物/非破坏追加）是否有脚本/护栏/校验器兜底，还是仅靠 LLM 自觉遵守 | P0     | W3         |
| D2   | 价值权重是否错配：是否把优化精力堆在低弹性杠杆上（从其他场景借来的手段、实际近似零作用的指标），而真正起作用的因素反被忽视 | P1     | W3         |
| D3   | 输入契约是否有缺口：被触发时所需的必填输入（素材/路径/上下文）是否有来源声明，缺失时是显式中止还是静默跳过/降级 | P1     | W3         |
| D4   | 是否与其他技能抢字段：被编排层调用时是否与其他技能修改同一输出字段/文件区域，导致一方静默覆盖另一方 | P1     | W3         |

## 阈值

- 评审时**逐项扫描**，命中即由 W2/W3/W7 落成段落
- 未命中**不写占位**
- 每条结论**必须**给出至少一个文件名作为证据
- W6 工程化档位以**未命中数**为依据：
  - ≤ 5 项未命中 → 稳定可复用
  - 6 – 12 → 半产品化
  - 13 – 20 → 执行说明
  - ≥ 21 → 想法阶段

## 维度映射表

> 本表建立 9 维度检查清单与外部规范体系的对应关系，确保审查标准一致性。

### 与 Karpathy 四原则的映射

| Karpathy 原则         | 对应检查项     | 映射说明                                    |
| --------------------- | -------------- | ------------------------------------------- |
| Think Before Coding   | M7, O2, O3     | 假设显式化、执行迭代、轨迹阅读              |
| Simplicity First      | C2, S4, C1     | 范围内聚、主文档精简、删除通用知识          |
| Surgical Changes      | M5, S1, S3     | 破坏性操作 P-V-H、路由职责分离、README 分离 |
| Goal-Driven Execution | V1, V2, V3, M4 | 成功判定、字段检查、落地检查、验证闭环      |

### 与 5 阶段审查流程的映射

| 5 阶段      | 对应检查项   | 映射说明         |
| ----------- | ------------ | ---------------- |
| 1. 结构审查 | S1-S6, C1-C4 | 结构与上下文预算 |
| 2. 内容审查 | O1-O3, M1-M7 | 起源与模式深度   |
| 3. 触发审查 | T1-T5, B3    | 触发与意图       |
| 4. 脚本审查 | P1-P7, I1-I3 | 实现与脚本设计   |
| 5. 验证审查 | V1-V7, B1-B4 | 验证闭环与边界   |
| 0. 方向审查（前置） | D1-D4 + 三段式元框架 | 第一性锚定 + 对抗式审查 |

### 优先级统一标准

| 级别   | 定义                                       | 行动     |
| ------ | ------------------------------------------ | -------- |
| **P0** | 阻塞使用：Agent 挂死、触发失败、合规不通过 | 必须修复 |
| **P1** | 维护风险：知识过期、职责漂移、可维护性下降 | 应当修复 |
| **P2** | 演进风险：环境绑定、缺少自检、可扩展性不足 | 建议修复 |
