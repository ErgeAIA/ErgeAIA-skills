# 评审标准（review）

## 三轴（一级质量模型）

| 轴 | 问题 | 主要看什么 |
| --- | --- | --- |
| **T — Trigger** | 触发正确吗？ | `description` 语义精度、触发词、Not for 边界、误触发风险 |
| **E — Execution** | 执行正确吗？ | 步骤可执行、输入输出契约、失败路径、HARD 护栏、脚本纪律（若有 scripts） |
| **C — Context** | 上下文成本合理吗？ | 主文档体量、是否全量堆砌、references 是否按需、无死链 |

高风险 skill 另加 **Safety/Contract**（非破坏、密钥、破坏性操作护栏）——仅在存在写盘/发布/覆盖类能力时启用。

不再默认并行维护「6 维复杂度 + 54 项 checklist + 8 维加权」三套重叠体系。

## L0 快速审查（默认）

适用于「帮我看看这个 skill / 评审一下」。

1. Frontmatter：`name`/`description`/version SSOT，字段是否越权。
2. Description：能否说清做什么、何时触发、边界。
3. 主职责：是否是一个连贯用户任务单元（内聚，而非机械「一步」）。
4. 主文档体量与结构：是否只做路由与硬边界。
5. references 结构：是否存在、是否声明何时加载、有无明显死链。
6. 明显冲突：同一规则多文件表述是否打架（只看已打开的文件，不默认全量读）。
7. 输出契约：是否说清必须产出什么。

产出短报告（见下），不强制优点数量，不写固定收尾套话。

## L1 深度审查（疑点或显式要求）

在 L0 之上，按疑点展开：

- 第一性锚定：该 skill 真正应解决什么；当前设计是否错位。
- T/E/C 逐轴证据化 findings（文件:位置）。
- CONDITIONAL 项：仅当目标具备对应能力时检查（scripts / 评测 / 编排字段等）。
- 安全与非破坏：若目标会改文件或被自动执行。
- 钢人/对抗：**仅用于方向性争议**；格式与触发层问题直接清单 + 证据，不升级论证仪式。

禁止：进入问题扫描前强制读完目标全部 `references/` 与 `scripts/`。  
证据不够 → 标明「未验证」或升级读取预算，而不是用猜测填报告。

## L2 评测（条件）

仅当：用户要求 benchmark/触发率/回归；或 description 高误触发风险需要实测。

相关脚本与 agents 已移至 `docs/archive/`。需要时从归档启用，并在报告中写明使用了归档工具链。

## 规则在评审中的用法

| 级别 | 报告中的表现 |
| --- | --- |
| HARD 失败 | P0/P1 级；阻塞「通过」 |
| CONDITIONAL 不满足且条件成立 | 按影响定 P1/P2 |
| CONDITIONAL 条件不成立 | N/A，不写入问题清单凑数 |
| HEURISTIC | 「建议」区；不与 HARD 混排 |

### 职责内聚（Cohesive Responsibility）

- 合理：围绕一个连贯用户任务的多步骤闭环（研究→产出→交付可以是一个 skill）。
- 不合理：把互不相关的能力塞进同一 description；或仅因「步骤≥2」要求拆分。
- 无职责耦合 → 结论写 **无需拆分**。

### 条件项速查（曾经的硬规则）

| 项 | 现规则 |
| --- | --- |
| I2 必须有脚本 | 无 scripts → N/A；有则查 P 系列（无交互、help、退出码、流分离） |
| V4/V5 评测集 | 仅 L2 / 高风险 / 用户要求 |
| D4 字段争用 | 仅有编排方或共享输出时 |
| F1 家族差分 | 仅显式要求或产品族 baseline；默认不跑 |
| O1 源自真实任务 | 质量证据，非硬缺陷 |
| M1 Gotchas | 有则强；无 Gotchas ≠ 错；仅当已知反直觉失败未告知才是问题 |
| 版本三处块 | 取消默认硬约束；SSOT = `metadata.version` + `CHANGELOG.md` |

### 明确废除

- W2 强制 3–5 条优点 → 改为 0–N 条有证据的可保留设计。
- W4 强制拆分候选 → 改为查职责耦合，无则「无需拆分」。
- W6 固定「若目标是 A/B」套话 → 删除；只保留状态/最强项/最大短板/是否建议继续重构。
- 固定 W1→W7 全量流水线与八段标准化审计文书作为默认路径。

## 默认报告结构（L0/L1）

1. **一句话结论**：当前状态。
2. **第一性判断**（L1 或方向存疑时）：它真正应解决什么。
3. **值得保留的设计**：0–N 条有证据的设计，无则省略整节。
4. **问题清单**：按 P0/P1/P2；每条含证据位置与级别（HARD/CONDITIONAL/HEURISTIC）。
5. **最值得做的动作**：≤3 条，按收益排序。
6. **是否值得继续重构**：是/否 + 一句理由。

证据矩阵、完整 checklist 留痕仅在 L1 且用户需要时附录。

## 论证质量（L1 方向性争议）

- 第一性锚定从本质矛盾推导，不写空洞「必须/绝不」填空。
- 若使用钢人：反方必须是最强反方；结论带条件；可检验变量尽量已检验。
- 格式/触发层决策禁止为凑流程硬升级成钢人论文。
- 无产物的步骤 = 未执行；报告里必须能看到结论。

## 评审者边界

- 裁判不下场：评审默认只出报告与整改方向，不直接改用户文件。
- 创建/重构属于构建路径：走 creation + validate；破坏性写入须 plan-gate。
- 「做法优于答案」：指出违背的原则与整改方向，不把整份修复稿塞进评审报告（除非用户明确要求全文改写且授权写文件）。
