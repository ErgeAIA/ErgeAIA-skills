# 如何写好一个 Skill

<!-- @类型: 参考指南 -->
<!-- @目的: 总结编写高质量目标 Skill 的核心方法、检查项与常见误区 -->
<!-- @场景: 从零创建 Skill、重写已有 Skill、整理散乱说明为可执行文档 -->
<!-- @触发条件: 当你需要把“一个想法”整理成“可触发、可执行、可验证的 Skill”时 -->

> **一句话**: 好 Skill 不是“写得多”，而是“触发准、步骤清、资源对、校验硬、迭代快”
> **版本**: v1.8.0
> **用途**: 编写高质量目标 Skill 的总览参考
> **适用范围**: 所有目标 Skill

## 1. 先定义：这个 Skill 到底解决什么问题

在开始写 `SKILL.md` 之前，先用一句话回答下面 4 个问题：

1. **用户会在什么场景下用它**
2. **它应该触发什么，不触发什么**
3. **触发后 Claude 需要遵循什么流程**
4. **哪些要求必须靠脚本或校验器保证**

如果这 4 个问题还说不清，先不要急着写长文档。

@提示: 一个好 Skill 通常只解决一类稳定问题，而不是把相邻但不同的任务全部塞进同一个 Skill。

## 2. 先写触发，再写细节

最先决定质量上限的，通常不是正文长度，而是 `description` 和触发示例是否准确。

写好触发描述时，优先满足这几个标准：

- **场景明确**：说明“用户说什么/想做什么时”应触发
- **边界清楚**：说明哪些相似请求不应该触发
- **动作导向**：描述任务，而不是泛泛描述主题
- **可盲测**：别人只看 `description`，也能大致判断是否应该触发

推荐自检：

- 把 `description` 单独拿出来看，能否判断是否适合当前请求
- 是否包含过宽表述，如“帮助处理开发任务”“辅助分析问题”
- 是否缺少触发语句、输入类型、任务对象等关键信息

## 3. 主文档只保留真正影响执行的内容

一个高质量 `SKILL.md` 应该像“执行手册”，而不是“产品介绍”。

正文优先保留：

- 主工作流
- 关键决策点
- 成功标准
- 失败信号与排查方法
- 去哪里读取额外参考

正文尽量不要堆积：

- 大段背景介绍
- 重复解释
- 多个变体混写
- 长模板、长示例、长表格
- 只有人类读者才关心的说明性文字

@提示: 默认假设模型已经很聪明。真正该写的是“它不知道但又必须知道的约束”。

## 4. 工作流要写成“能执行”的步骤，不要写成散文

判断一个 Skill 是否好用，关键看 Claude 触发后能不能稳定落到动作上。

推荐写法：

- 用 `## @工作流:` 描述主流程
- 用 `### @步骤N:` 切成顺序清晰的步骤
- 每步至少写清：
  - `@类型`
  - `@优先级`
  - `@验证点`
  - `@验证方式`
- 可执行事项统一用 `- @动作:`

好的步骤通常具备 4 个特征：

- **原子**：一步只做一件事
- **可判断**：执行者知道何时算完成
- **可验证**：能检查结果是否正确
- **可衔接**：和前后步骤关系清楚

如果流程里存在分支，优先写“默认路径 + 分支条件”，不要从一开始就把所有例外铺开。

## 5. 能下沉的都下沉到 references/

当 `SKILL.md` 开始变长、变杂、变难扫时，通常不是“应该删”，而是“应该拆”。

适合放进 `references/` 的内容：

- 大段规则说明
- 多框架 / 多提供商 / 多业务域变体
- 模板、范例、长代码片段
- 排错手册
- 次级流程与扩展场景
- 高频使用场景下的输入模板、可复制示例提问、一次性材料清单

正文里要写清楚：

- **什么时候读哪份参考**
- **读它是为了回答什么问题**

如果你准备补“场景输入模板”，优先采用下面的分工：

- `SKILL.md`：负责路由、决策、步骤与进入条件
- `references/templates/*.md`：负责沉淀固定模板来源；优先复制 [scenario-input-template.md](../templates/scenario-input-template.md) 的固定结构，再按场景做最小改写
- `references/examples/*.md`：负责沉淀从工作流自动生成或继续人工收敛的场景示例文档

@提示: 固定模板来源放在 `references/templates/`；自动生成的示例文档放在 `references/examples/`，两者职责不要混淆。

@提示: 若目标 Skill 的 `SKILL.md` 已经写出较完整的 `## @工作流:`、`@场景`、`@目的` 与 `- @动作:`，可直接运行 `python scripts/skill_cli.py generate-templates <skill-path>` 生成一批场景示例草稿，并顺带更新 `references/examples/index.md`。

@警告: 模板文档不应成为路由依据。不要让“模板里怎么写”反过来定义 Skill 的主流程。
@警告: 模板文档中应显式写出“本文档不负责工作流路由”。
@警告: 每个高频场景的输入模板默认应收敛到 1 个主模板；只有在存在稳定、长期复用的场景分支时，才扩展到 2-3 个模板。若超过 3 个，优先反查是否只是“同一场景下不同目的”的差异。
@提示: 固定结构建议至少包含 `适用场景`、`建议提供的信息`、`可直接复制输入模板`，并把“当前目标 / 最关注点 / 期望结果”合并写在 `适用场景` 内，避免重复。

不要只扔一个裸链接，不说明使用时机。

## 6. 把“必须正确”的约束固化到 scripts/

当某些规则不能靠自然语言稳定保证时，就应该上脚本。

优先考虑放进 `scripts/validate_skill.py` 的内容：

- 结构检查
- frontmatter 校验
- 版本一致性
- 固定格式输出约束
- 文件存在性与命名规则
- 机器可判定的合规条件

适合放进 `scripts/run.py` 或其他执行脚本的内容：

- 批量处理
- 易错操作
- 需要稳定落盘的动作
- 多步工程化执行流程

原则很简单：

- **语言擅长判断策略与流程**
- **脚本擅长保证确定性与格式正确**

## 7. assets/ 只放真正会被使用的资源

`assets/` 里应该放最终真的会参与输出或执行的文件，例如：

- 模板文件
- 示例文件
- 静态页面
- 图标、示意图、样例资源

不要因为“结构完整”就预置无用占位文件。空目录可以保留，但无用文件不应生成。

## 8. 写完后用这份清单检查

### 8.1 触发是否准确

- `name` 是否是稳定、清晰的 `kebab-case`
- `description` 是否能说明“何时触发”
- 是否能区分“应该触发”和“不应该触发”的相邻请求

### 8.2 结构是否完整

- 是否有 `SKILL.md`
- 是否有 `## @工作流:`
- 是否有 `### @步骤N:`
- 是否有 HTML 注释元数据
- 是否用 `- @动作:` 表达可执行事项

### 8.3 内容是否克制

- 正文是否只保留主流程和关键约束
- 长示例和变体是否已下沉到 `references/`
- `assets/` 是否只保留真实使用的资源
- 是否避免了 README / CHANGELOG 等冗余文件

### 8.4 版本是否同步

- frontmatter `version`
- 标题下版本块
- 文末首条版本历史

三者必须一致。

### 8.5 校验是否闭环

- `python scripts/skill_cli.py validate <skill-dir>` 通过
- 若目标 Skill 提供 `scripts/validate_skill.py`，其硬校验也通过
- 需要时补充 `eval-set`，验证触发边界是否准确

## 9. 常见误区

### 误区 1：把 Skill 写成百科

表现：背景很多，步骤很少。

修正：删背景、补动作、补验证。

### 误区 2：把多个任务硬塞进一个 Skill

表现：触发条件过宽，流程混乱，用户一改措辞就容易误触发。

修正：按任务目标拆 Skill，不按“大主题”聚合。

### 误区 3：只有自然语言，没有硬校验

表现：文档看起来完整，但一涉及格式、命名、落盘就容易漂移。

修正：把可判定约束下沉到 `scripts/validate_skill.py`。

### 误区 4：references 很多，但没有导航

表现：资料都在，但 Claude 不知道什么时候该读哪份。

修正：在正文里明确“何时读取哪份参考”。

### 误区 5：每次改动都忘记同步版本

表现：frontmatter、标题版本、版本历史不一致。

修正：把版本更新纳入每次修改后的固定动作。

## 10. 一句话标准

如果一个 Skill 能做到下面这 5 点，通常就已经很好用了：

- **触发准**：该触发时触发，不该触发时不乱入
- **步骤清**：触发后能稳定落到动作
- **资源对**：参考、脚本、资产各归其位
- **校验硬**：关键约束可被代码验证
- **迭代快**：真实使用后能快速修正文档和脚本
