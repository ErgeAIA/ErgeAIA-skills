## 1. 什么时候用这份参考

### @步骤1: 判断是否需要进入 workflow 设计

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @验证点: 已判断目标 Skill 是否需要做业务流程到 workflow 的映射 -->
<!-- @验证方式: 记录轻量 / 中等 / 复杂分级，以及是否进入映射流程 -->
<!-- @ID: step-decide-whether-to-map -->

这份参考不是所有 Skill 的必修课。

- **轻量 Skill**：单一任务、低分支、低回环、边界天然清晰，通常可以跳过完整映射
- **中等 Skill**：有 2-3 个阶段，存在少量检查点或局部分支，建议做简化映射
- **复杂 Skill**：多阶段、多产物、多回环、存在明显边界或重构需求，必须先做映射

- @动作: 若判断为轻量 Skill，记录跳过完整映射的原因
- @动作: 若判断为复杂 Skill，标记“workflow 映射表”为必填项

## 2. 开始前先统一确认

### @步骤2: 一次性确认所有关键问题

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @验证点: 已先确认是否进入该流程，且关键问题已一次性确认 -->
<!-- @验证方式: 检查是否存在统一确认清单与确认结论 -->
<!-- @ID: step-confirm-before-mapping -->

进入映射前，先确认：

- 是否真的需要进入当前流程
- 当前任务是新建、更新，还是重构已有 Skill
- 交付物是设计草案、正式 Skill，还是参考文档补充
- 哪些要求是硬规则，哪些仅作为建议

@提示: 若需要确认，不要边做边问。先集中列出问题，再一次性与用户确认。

- @动作: 整理统一确认清单
- @动作: 把确认结论写入 `design.md` 或同等设计文档

## 3. 三层边界：业务流程 / workflow / 步骤

### @步骤3: 区分三层结构

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @验证点: 已能区分业务流程、workflow 与步骤 -->
<!-- @验证方式: 检查设计文档是否分别描述三层内容，而未相互混写 -->
<!-- @ID: step-separate-three-layers -->

- **业务流程**：真实业务如何运转，例如“确定要求 -> 生成计划 -> 产出内容 -> 检查 -> 修正 -> 终稿 -> 回写”
- **workflow**：Skill 要提供的可独立能力单元，例如“出题”“解析”“终稿审校”“台账回写”
- **步骤**：单个 workflow 内部的执行顺序，例如“读取约束 -> 生成草稿 -> 自检 -> 输出”

@警告: 不要把业务步骤机械翻译成 workflow，也不要把多个独立能力硬塞进一个 workflow。

## 4. 复杂度判断门

### @步骤4: 用判断门决定设计强度

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @验证点: 已基于复杂度判断决定采用轻量、简化或完整映射 -->
<!-- @验证方式: 检查设计文档是否记录判断结果与依据 -->
<!-- @ID: step-apply-complexity-gate -->

建议至少回答下面 5 个问题：

| 判断问题 | 是 / 否 |
|---|---|
| 是否存在多个阶段性产物 |  |
| 是否存在明显检查 / 修订节点 |  |
| 是否存在回环 |  |
| 是否存在多个可独立触发的用户意图 |  |
| 是否预计持续扩展 |  |

建议解释：

- 大多为“否” -> 轻量 Skill
- 有 2-3 项为“是” -> 中等 Skill，建议做简化映射
- 大多为“是” -> 复杂 Skill，必须做完整映射

## 5. 如何决定主 workflow、子 workflow 与普通步骤

### @步骤5: 选择合适的抽象层级

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @验证点: 已判断关键能力应升格为主 workflow、子 workflow，还是普通步骤 -->
<!-- @验证方式: 检查设计文档是否为关键能力标注层级及理由 -->
<!-- @ID: step-choose-abstraction-level -->

优先成为**主 workflow**的能力通常满足：

- 对应稳定的用户意图
- 可单独触发
- 有相对独立的输入和输出
- 未来可能被反复复用

更适合做**子 workflow**的能力通常满足：

- 总是附属于某个主 workflow
- 很少被用户单独请求
- 主要承担阶段性检查、中间转换或局部回路

只应保留为**普通步骤**的动作通常满足：

- 高度局部
- 仅在当前上下文使用
- 不构成稳定意图
- 不值得单独复用

## 6. workflow 映射表

### @步骤6: 为复杂 Skill 产出必填映射表

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @验证点: 复杂 Skill 已产出 workflow 映射表，中等 Skill 已决定是否简化产出 -->
<!-- @验证方式: 检查设计文档中是否存在映射表，并覆盖必要字段 -->
<!-- @ID: step-produce-mapping-table -->

对复杂 Skill，workflow 映射表是必填项。建议至少写在 `design.md` 或同等设计文档中。

推荐字段：

| 工作流 | 类型 | 做什么 | 不做什么 | 上游 | 下游 | 失败回流 | 可否单独触发 |
|---|---|---|---|---|---|---|---|

@提示: 这张表的目标不是写给最终用户看，而是确保 Skill 创建者先把边界设计清楚。

- @动作: 对复杂 Skill，先写映射表，再开始写目标 Skill 的 `SKILL.md`
- @动作: 对中等 Skill，若边界已足够清晰，可产出简化版表格

## 7. 把设计期映射落成运行期识别结构

### @步骤7: 优先把中复杂 Skill 的主路由写成“决策矩阵 + 强规则摘要”

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @验证点: 已判断目标 Skill 是否应把 workflow 映射表继续落成运行期识别矩阵 -->
<!-- @验证方式: 检查设计文档或主 `SKILL.md` 规划中是否明确采用矩阵、适用条件、反例条件与强规则摘要 -->
<!-- @ID: step-convert-mapping-into-routing-matrix -->

`workflow 映射表` 解决的是设计期边界问题，但它通常还不是另一个 Claude 在运行期最容易命中的结构。对于中等与复杂 Skill，尤其是存在多个稳定用户意图时，推荐再往前走一步：把设计期映射落成主 `SKILL.md` 中的“决策矩阵 + 强规则摘要”。

优先采用这套结构的典型信号：

- 存在 3 个及以上稳定用户意图
- 多个 workflow 的触发词容易混淆
- 旧决策树已经变长、变脆、难维护
- 需要降低主文档 token / 行数
- 需要给 `validate` 或目标 Skill 的 `scripts/validate_skill.py` 提供稳定锚点

不建议机械套用的反例条件：

- 目标 Skill 只有 1-2 个稳定意图
- workflow 极少，几乎没有识别歧义
- 目标 Skill 没有仓库级 / 领域级强规则需要摘要化
- 表格化后的路由信息并不会比简短 bullets 更清楚

推荐把运行期识别结构写成两层：

1. **决策矩阵**：只负责“用户说什么 -> 命中哪条 workflow”
2. **强规则摘要**：只负责“命中后必须遵守的硬约束、优先入口和禁止事项”

推荐矩阵列：

| 场景 | 命中信号 | 跳转到 |
|---|---|---|

- @动作: 对中复杂 Skill，先用 `workflow 映射表` 列出稳定能力边界，再决定哪些行真正值得进入运行期矩阵；不要把所有设计期表项原封不动搬进主文档
- @动作: 矩阵里的 `命中信号` 只写高信号、稳定、可复述的用户说法或关键词，不在此处展开实现细节
- @动作: `跳转到` 只写 workflow、reference 或输入模板入口，不在矩阵单元格里塞长说明
- @动作: 若目标 Skill 已维护 `references/examples/input-template-*.md`，且主文档采用了决策矩阵，优先在 `references/examples/index.md` 补“决策矩阵命中速查”，把用户原话、矩阵命中和模板入口连起来
- @动作: 若只剩极少数意图且没有混淆空间，记录“不采用矩阵”的原因即可，不要为了统一形式硬造表格

## 8. 回环与终稿节点

### @步骤8: 显式识别回环与最终审校

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @验证点: 已标出整体回环、局部回环和终稿节点 -->
<!-- @验证方式: 检查设计文档是否说明失败回流路径与最终审校位置 -->
<!-- @ID: step-identify-loops-and-final-check -->

真实业务通常不是线性的。

- **整体回环**：整条主链不通过后，需要整体回退重做
- **局部回环**：只让局部单元重新经过“生成 -> 检查 -> 修正”
- **终稿节点**：关注是否可交付、是否一致、格式是否兼容、字段是否合法

@提示: “写出来”不等于“能交付”。终稿审校通常值得被单独识别。

## 9. 重构触发器（建议清单）

### @步骤9: 用建议清单判断是否需要停下重构

<!-- @类型: 操作步骤 -->
<!-- @优先级: 可选 -->
<!-- @验证点: 已判断是否存在 workflow 重构信号 -->
<!-- @验证方式: 检查是否根据建议清单记录了重构判断 -->
<!-- @ID: step-check-refactor-triggers -->

下面这些信号说明：也许不该继续在旧结构上打补丁，而该先重构 workflow。

- 原本单一任务已经变成多阶段流程
- 同一个 workflow 同时承担“生产 + 检查 + 修正 + 终稿”
- 用户意图已分化，但 Skill 仍只有单一路径
- 返工路径成为高频模式，却没有显式建模
- 维护时经常出现“这个环节到底归谁负责”的争议

@提示: 这是一份建议清单，不是硬规则。它的作用是提醒你停下来复盘结构，而不是自动判定必须重构。
