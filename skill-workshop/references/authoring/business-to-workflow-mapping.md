## 1. 什么时候用这份参考

这份参考不是所有 Skill 的必修课：

- **轻量 Skill**：单一任务、低分支、低回环、边界天然清晰，通常可以跳过完整映射（记录跳过原因）
- **中等 Skill**：有 2-3 个阶段，存在少量检查点或局部分支，建议做简化映射
- **复杂 Skill**：多阶段、多产物、多回环、存在明显边界或重构需求，必须先做映射（映射表为必填项）

## 2. 开始前先统一确认

一次性集中确认（不要边做边问）：当前任务是新建/更新/重构、交付物形态（设计草案/正式 Skill/参考文档）、哪些是硬规则哪些是建议。确认结论写入 `design.md` 或同等设计文档。

## 3. 三层边界：业务流程 / workflow / 步骤

- **业务流程**：真实业务如何运转，例如“确定要求 -> 生成计划 -> 产出内容 -> 检查 -> 修正 -> 终稿 -> 回写”
- **workflow**：Skill 要提供的可独立能力单元，例如“出题”“解析”“终稿审校”“台账回写”
- **步骤**：单个 workflow 内部的执行顺序，例如“读取约束 -> 生成草稿 -> 自检 -> 输出”

@警告: 不要把业务步骤机械翻译成 workflow，也不要把多个独立能力硬塞进一个 workflow。

## 4. 复杂度判断门

复杂度档位判定直接复用 `references/rubrics/complexity-rubric.md`（六维标尺，W1 同款）。判断结果决定映射强度：轻量跳过完整映射（记录原因）、中等做简化映射、复杂必须做完整映射。

## 5. 如何决定主 workflow、子 workflow 与普通步骤

优先成为**主 workflow**的能力通常满足：

- 对应稳定的用户意图
- 可单独触发
- 有相对独立的输入和输出
- 未来可能被反复复用

更适合做**子 workflow**的能力通常满足：

- 总是附属于某个主 workflow
- 很少被用户单独请求
- 主要承担阶段性检查、中间转换或局部回路

只应保留为**普通步骤**的动作通常满足：

- 高度局部
- 仅在当前上下文使用
- 不构成稳定意图
- 不值得单独复用

## 6. workflow 映射表

对复杂 Skill，workflow 映射表是必填项，写在 `design.md` 或同等设计文档中（中等 Skill 可产出简化版）。

推荐字段：

| 工作流 | 类型 | 做什么 | 不做什么 | 上游 | 下游 | 失败回流 | 可否单独触发 |
|---|---|---|---|---|---|---|---|

@提示: 这张表的目标不是写给最终用户看，而是确保 Skill 创建者先把边界设计清楚。

## 7. 把设计期映射落成运行期识别结构

`workflow 映射表` 解决的是设计期边界问题，但它通常还不是另一个 Claude 在运行期最容易命中的结构。对于中等与复杂 Skill，尤其是存在多个稳定用户意图时，推荐再往前走一步：把设计期映射落成主 `SKILL.md` 中的“决策矩阵 + 强规则摘要”。

优先采用这套结构的典型信号：

- 存在 3 个及以上稳定用户意图
- 多个 workflow 的触发词容易混淆
- 旧决策树已经变长、变脆、难维护
- 需要降低主文档 token / 行数
- 需要给 `validate` 或目标 Skill 的 `scripts/validate_skill.py` 提供稳定锚点

不建议机械套用的反例条件：

- 目标 Skill 只有 1-2 个稳定意图
- workflow 极少，几乎没有识别歧义
- 目标 Skill 没有仓库级 / 领域级强规则需要摘要化
- 表格化后的路由信息并不会比简短 bullets 更清楚

推荐把运行期识别结构写成两层：

1. **决策矩阵**：只负责“用户说什么 -> 命中哪条 workflow”
2. **强规则摘要**：只负责“命中后必须遵守的硬约束、优先入口和禁止事项”

推荐矩阵列：

| 场景 | 命中信号 | 跳转到 |
|---|---|---|

- @动作: 对中复杂 Skill，先用 `workflow 映射表` 列出稳定能力边界，再决定哪些行真正值得进入运行期矩阵；不要把所有设计期表项原封不动搬进主文档
- @动作: 矩阵里的 `命中信号` 只写高信号、稳定、可复述的用户说法或关键词，不在此处展开实现细节
- @动作: `跳转到` 只写 workflow、reference 或输入模板入口，不在矩阵单元格里塞长说明
- @动作: 若目标 Skill 已维护 `references/examples/input-template-*.md`，且主文档采用了决策矩阵，优先在 `references/examples/index.md` 补“决策矩阵命中速查”，把用户原话、矩阵命中和模板入口连起来
- @动作: 若只剩极少数意图且没有混淆空间，记录“不采用矩阵”的原因即可，不要为了统一形式硬造表格

## 8. 回环与终稿节点

真实业务通常不是线性的：

- **整体回环**：整条主链不通过后，需要整体回退重做
- **局部回环**：只让局部单元重新经过“生成 -> 检查 -> 修正”
- **终稿节点**：关注是否可交付、是否一致、格式是否兼容、字段是否合法

@提示: “写出来”不等于“能交付”。终稿审校通常值得被单独识别。

## 9. 重构触发器（建议清单）

下面这些信号说明：也许不该继续在旧结构上打补丁，而该先重构 workflow。

- 原本单一任务已经变成多阶段流程
- 同一个 workflow 同时承担“生产 + 检查 + 修正 + 终稿”
- 用户意图已分化，但 Skill 仍只有单一路径
- 返工路径成为高频模式，却没有显式建模
- 维护时经常出现“这个环节到底归谁负责”的争议

@提示: 这是一份建议清单，不是硬规则。它的作用是提醒你停下来复盘结构，而不是自动判定必须重构。
