# Skill / 指令资产结构评估工作流参考

> **一句话**: 先收集证据、再跑校验、后下结论，最后把评估结果沉淀成可复用文档
> **版本**: v1.3.4
> **用途**: 指导 Skill / 指令资产结构评估与评估报告写作
> **适用范围**: 目标 Skill 或相关可复用指令资产的结构质量审查、重构优先级判断与文档化反馈

## 1. 文档定位

### @步骤1: 先确认这是不是“结构评估”任务

这份参考负责的是：

- 评价一个已有 Skill 或相关可复用指令资产当前写得怎么样
- 找出结构硬伤、主文档职责问题、指令边界问题、references 分层问题与验证缺口
- 给出优先级清晰的重构建议
- 产出可保存、可复用的评估文档

这份参考不负责的是：

- 不替代从零创建 Skill 的流程
- 不默认直接改写目标 Skill
- 不替代自动化 `eval-loop`

@提示: 如果用户已经明确要求“直接重构这个 Skill / 指令资产”，先做结构评估，再决定是否进入 [skill-refactoring-workflow.md](skill-refactoring-workflow.md)。

## 2. 推荐证据范围

### @步骤2: 先盘点应该看哪些文件

默认至少检查：

- 若目标是 Skill 目录：`SKILL.md`
- 若目标是独立指令资产：主指令文档本体（如 workflow prompt、agent instruction、评测模板）
- `README.md` 或同类说明文档（若存在）
- 关键 companion files：如 `checklist.md`、`examples.md`、`templates/`、`references/`
- `scripts/validate_skill.py` 或其他工程硬校验入口（若存在）
- `python scripts/skill_cli.py validate <skill-dir>` 的校验输出（仅当目标是 Skill 目录时）

如果目标 Skill 体量较大，先建立“最小必读证据清单”，避免一次性加载全部内容。

@提示: 目标是“证据够支持结论”，不是“把所有文件都读完”。

## 3. 评测工作流

## @工作流: 评测已有 Skill / 指令资产 并输出评估文档

### @步骤3: 先确认输出约束与保存路径

统一确认时，至少问清或推断：

- 是否需要保存成文档
- 评估文档默认落在哪个路径
- 是否需要隐藏本技能名称
- 是否需要使用第一人称、团队口径或用户指定代称

- @动作: 若用户要求保存评估结果，Skill 目录默认写入 `<target-skill>/skill-evaluation.md`；单文件指令资产默认写入同目录的 `<target-file-stem>.evaluation.md`
- @动作: 若用户要求隐藏本技能名称，在报告 frontmatter 与正文中用用户指定称呼替换；未指定时可使用“我”
- @动作: 若用户明显是在请求评测，但输入约束不完整，优先根据目标路径、是否保存、命名隐藏和评估重点自行补齐；只有存在高风险歧义时再集中确认

### @步骤4: 先读主文档，再按目标类型读 companion files

推荐顺序：

1. 若目标是 Skill 目录，先看 `SKILL.md`；若目标是独立指令资产，先看主指令文档
2. 若目标 Skill 存在 `README.md` 或同类说明文档，再看它
3. 再根据主文档引用关系或实际文件结构，按需读取关键 companion files

当你发现用户请求缺了保存路径、命名隐藏或评估重点等约束时，优先按默认规则处理：Skill 目录保存到 `<target-skill>/skill-evaluation.md`，单文件指令资产保存到同目录的 `<target-file-stem>.evaluation.md`，命名隐藏按用户原话替换，评估重点以结构质量、可维护性和验证闭环为主。

@提示: 若目标 Skill 或主指令文档已经把“结构评测”前置为运行期入口，优先沿主文档给出的 reference 入口取证，不要把 `README.md` 当成必有文件。
@警告: 不要默认把所有 examples 全量读入上下文，尤其是大型示例库。

### @步骤5: 能跑 validate 时先跑 validate，再看人工结构问题

若目标是 Skill 目录，统一先跑：

```bash
python scripts/skill_cli.py validate <path_to_skill_folder>
```

必要时再补：

```bash
cd <path_to_skill_folder>
python scripts/validate_skill.py --skill .
```

若目标不是 Skill 目录，不要为了形式统一而强行套 `skill_cli.py validate`；改为：

- 明确记录“当前目标不适用 Skill 目录级 validate”
- 盘点是否存在等价脚本、lint、模板校验或引用一致性检查入口
- 若没有适用硬校验，明确把这点写入评估文档的 `limitations` 或验证缺口

- @动作: 把 `validate` 输出中与 frontmatter、语义化标记、版本、链接、版本历史有关的错误写入证据
- @动作: 若目标不是 Skill 目录，把“为什么没有跑 validate、是否存在替代校验”写入证据
- @动作: 区分“校验器已证明的问题”和“基于结构口径的判断问题”

### @步骤6: 用结构口径判断复杂度、优点与主要问题

评估时重点看，并统一压缩为 8 个主维度：

| 维度 | 权重 | 重点关注 |
| --- | ---: | --- |
| 目标与适用边界 | 15% | 目标是否清楚、触发边界是否稳定、是否容易误分流 |
| 指令一致性与精准性 | 15% | 指令是否支持目标，是否存在模糊词、冲突或隐含假设 |
| 输入输出契约 | 15% | 输入要求、输出结构、缺失输入处理是否清楚 |
| 工作流完整性 | 15% | 是否存在稳定可执行的最小步骤链与默认动作 |
| 鲁棒性与安全边界 | 15% | 对异常、缺失材料、越界执行和风险场景的处理是否稳健 |
| 可维护性与渐进披露 | 10% | 主文档是否仍是路由层，references 是否分层清晰，是否重复维护 |
| 可验证性与测试闭环 | 10% | 是否有 `validate`、脚本入口、回归验证或评测闭环 |
| Token 效率与冗余控制 | 5% | 是否存在大段重复、低价值说明和可压缩冗余 |

- @动作: 每个维度单独打 `0-100` 分，并写 1 句主要扣分原因
- @动作: 最终总分按上述权重加权，得到 `总分 / 100`
- @动作: 问题排序优先看影响：先写会影响触发、执行、验证或长期维护的问题，再写局部表达优化

### @步骤7: 产出结构化评估报告

默认不要直接重写目标 Skill / 指令资产，除非用户明确要求。评估阶段的主要交付物应是评估文档。

- @动作: 使用本参考第 4 节的默认报告结构
- @动作: 报告中必须包含 8 维评分表、维度权重和加权总分
- @动作: 在报告中引用关键文件和必要的校验输出
- @动作: 给出“下一步应该重构什么、先改哪里”的顺序

## 4. 默认报告结构

### @步骤8: 用固定结构写评估文档

默认采用以下结构：

1. `评估范围`
2. `一句话结论`
3. `复杂度判断`
4. `8维评分表`
5. `主要优点`
6. `主要问题`
7. `拆分需求识别`
8. `整改方向`
9. `结构性问题总结`
10. `总评`

默认要求：

- frontmatter：`title`、`date`、`evaluator`、`framework`、`target`；建议补 `scope`、`limitations`
- `8维评分表` 必须使用以下 8 个维度，并统一显示“维度分 / 100”“权重”“主要扣分依据”
- `主要问题` 按优先级排序，并优先覆盖结构性硬伤
- 若跑过 `validate`，应写出关键结论；若出现硬错误，应显式落到 `主要问题`
- 若目标不是 Skill 目录，`target` 可填写主指令文档路径或目标对象名称，并在 `limitations` 里写清适用的校验边界

默认评分表字段：

| 维度 | 维度分 / 100 | 权重 | 主要扣分依据 |
| --- | ---: | ---: | --- |
| 目标与适用边界 |  | 15% |  |
| 指令一致性与精准性 |  | 15% |  |
| 输入输出契约 |  | 15% |  |
| 工作流完整性 |  | 15% |  |
| 鲁棒性与安全边界 |  | 15% |  |
| 可维护性与渐进披露 |  | 10% |  |
| 可验证性与测试闭环 |  | 10% |  |
| Token 效率与冗余控制 |  | 5% |  |

- 加权总分：`总分 / 100`
- 计算方式：各维度 `0-100` 分分别乘以权重后求和
- 输出要求：总分后必须补一句“主要扣分原因”，避免只给数字不给依据

默认映射建议：

| 加权总分 / 100 | 默认推荐重构方案 |
| --- | --- |
| `80-100` | 轻量修订 |
| `60-79` | 结构重整 |
| `<60` | 深度重构 |

- @动作: 先按总分区间给出默认推荐重构方案，再结合问题密度、单点致命风险和材料完整度判断是否需要覆盖默认映射
- @动作: 若覆盖默认映射，必须在报告中写明“为什么这次不按默认区间走”

- @动作: 生成正式评估文档时，优先复制 [evaluation-template.md](../templates/evaluation-template.md) 作为骨架，再按本 workflow 回填证据和结论
- @动作: 若希望让 8 维分数更稳定、可复核，先按 [weighted-scoring.md](../rubrics/weighted-scoring.md)「评分前复核」逐维标记 ✅/⚠️/❌ 再换算，然后回填正式评分表
- @动作: 若用户只需要简版结论，可在不删除 `8维评分表` 的前提下，压缩模板中的低优先级建议与说明文字

按需增强：

- 文件证据链接
- `validate` 的关键输出片段
- companion files 的职责证据
- `结构性问题总结`

@提示: 若用户要求隐藏本技能名称，可将 `framework` 写成用户指定称呼；未指定时可写 `我`。
@提示: 默认只维护这一套标准 `skill-evaluation.md` 结构，不额外拆出多套报告格式。

## 5. 常见结构问题

### @步骤9: 优先抓“结构性硬伤”

高频结构问题通常包括：

- Skill 目录缺失 frontmatter，或独立指令资产缺少最小元信息与用途声明
- 主文档没有采用语义化标记体系
- 主 `SKILL.md` 过厚，不再像路由层
- `README.md` 与主文档重复维护
- companion files 存在明显职责重叠
- references 很大，但主文档没有说明“何时读哪份”
- 没有明确验证入口，或只写了描述没有真正脚本入口

@提示: 这些问题的核心不是“写得好不好看”，而是“结构是否稳定、是否能长期维护、是否能被验证”。
