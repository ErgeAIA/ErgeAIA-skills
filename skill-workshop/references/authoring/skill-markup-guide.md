# Skill 语义化标记系统规范

<!-- @类型: Skill 概览 -->
<!-- @名称: Skill 语义化标记系统 -->
<!-- @适用场景: 编写与维护目标 Skill 的 SKILL.md / SOP 文档 -->
<!-- @主要工作流: 设计标记; 编写 SOP; 解析执行 -->

> **一句话**: 语义化标记系统的完整规范参考
> **版本**: v1.4.0

## 触发示例

- "如何编写 SKILL.md 的语义化标记？"
- "@工作流 和 @步骤 有什么区别？"
- "验证点应该怎么写？"

## 概述

本文档定义了目标 Skill 的 SKILL.md 文件的语义化标记系统，目标是：

- 为 AI 提供稳定、统一、可解析的结构化标记
- 降低 AI 从自然语言中“猜意图”的成本，提升 SOP 执行可靠性
- 支持多项目、多目录结构（单仓 / monorepo）之间的迁移复用

---

## 标记系统总览

所有语义化标记使用 `@` 前缀，统一格式为：

- 行内字段：`@标记名: 值`
- 标题字段：`## @工作流: 名称`、`### @步骤1: 标题`
- 注释元数据：`<!-- @键: 值 -->`（仅供机器读取，不影响渲染）

标记按用途分为：结构标记、动作标记、范围标记、信息标记、元数据标记、文档标记。

为降低歧义并提升可执行性，建议在同一工作流/步骤内遵循“单一事实来源 + 明确优先级”的解析规则（见第 8 节）。

## 1. 结构标记

结构标记用于描述「工作流 → 步骤 → 子步骤」的层级结构。

| 标记       | 用途                     | 示例                           |
|------------|--------------------------|--------------------------------|
| `@工作流:` | 定义标准操作流程(SOP)   | `## @工作流: 新增 core 页面`   |
| `@步骤0:`  | 前置准备步骤（统一用 0） | `### @步骤0: 确定项目根目录`   |
| `@步骤1:`  | 正式执行步骤（1,2,3…）   | `### @步骤1: 创建页面模块`     |
| `@步骤2:`  | 后续执行步骤（依次递增） | `### @步骤2: 注册路由标题`     |
| `@ID:`     | 机器友好 ID（注释中给出）| `<!-- @ID: step-create-page -->` |
| `@依赖:`   | 步骤对其他步骤/ID 的依赖 | `<!-- @依赖: step-locate-root -->` |
| `@跳转到:` | 决策树/分支跳转到某个 ID | `@跳转到: step-create-page`    |

**规范：**

- 工作流标题统一：`## @工作流: 名称`
- 步骤标题统一：`### @步骤0: ...`、`### @步骤1: ...`、`### @步骤2: ...`
- 建议每个工作流与关键步骤都在注释中定义唯一 `@ID`，供 `@跳转到` 精确引用
- `@ID` 命名建议使用 `kebab-case`（仅小写字母/数字/短横线），并使用前缀区分层级：
  - 工作流：`wf-...`
  - 步骤：`step-...`
  - 决策/分支：`br-...`

## 2. 动作、产物与验证标记

动作标记用于标明“真正需要执行的操作”，验证标记用于说明“要验证什么、如何验证”。

| 标记         | 用途                           | 示例                                             |
|--------------|--------------------------------|--------------------------------------------------|
| `@动作:`     | 需要执行的具体操作            | `- @动作: 在 xxx 下创建文件`                     |
| `@改动文件:` | 本步骤会修改/新增的文件范围   | `@改动文件: ${DASH_ROOT}/source/pages/**`        |
| `@产物:`     | 本步骤输出物（文件/配置项）   | `@产物: ${DASH_ROOT}/source/pages/a/b_page.py`   |
| `@验证点:`   | 要验证的结果 / 状态（what）   | `@验证点: 页面可正常访问，菜单显示正确`         |
| `@验证方式:` | 验证方法 / 手段（how）        | `@验证方式: 手动访问 URL，检查返回状态码`       |
| `@后置验证:` | 整个工作流结束后的验收标准    | `@后置验证: 新增页面可访问且权限规则正确`       |

**规范：**

- 在步骤正文中，所有可执行操作统一写成列表项：`- @动作: ...`
- 验证相关字段分工：
  - 步骤级：使用 `@验证点:` + `@验证方式:` 描述
  - 工作流级：使用 `@后置验证:` 描述整体验收标准
- 如需可选动作，可用自然语言说明：`- @动作(可选): ...` 或在步骤上用 `@优先级: 可选`
- `@改动文件` 与 `@产物` 优先写在标题下的 HTML 注释元数据中，减少正文与元数据重复带来的冲突

## 3. 范围与信息标记

这些标记为 AI 提供上下文、适用范围和辅助信息，用于“是否选择该 Skill / 工作流”。

| 标记       | 用途                         | 示例                                                 |
|------------|------------------------------|------------------------------------------------------|
| `@场景:`   | 适用场景描述                 | `@场景: 新增/修改页面与回调`                         |
| `@范围:`   | 适用范围（页面级 / 项目级） | `@范围: 页面级复用`                                  |
| `@入口:`   | 关键文件索引                 | `@入口: 应用装配 → ${DASH_ROOT}/source/server.py`   |
| `@注意:`   | 执行相关注意事项 / 风险点   | `@注意: 如需侧边菜单入口，需同步配置菜单映射`       |
| `@警告:`   | 严重风险、错误后果           | `@警告: 若未配置权限规则会被重定向到 403`           |
| `@提示:`   | 执行时的操作性提示           | `@提示: 以下所有路径均相对于 ${DASH_ROOT} 描述`     |
| `@说明:`   | 背景说明 / 设计原因          | `@说明: 在多端/monorepo 项目中需要先定位 Dash 子目录`|
| `@工具:`   | 工具/脚本说明                | `@工具: 使用脚手架脚本创建基础页面文件`             |

**约定：**

- `@提示:` 面向“怎么做更顺手/少踩坑”
- `@说明:` 面向“为什么要这么做/背景原因”

## 4. 元数据标记

元数据标记主要出现在 HTML 注释中，方便 AI 抽取整齐的键值对。

| 标记         | 用途                        | 示例                                         |
|--------------|-----------------------------|----------------------------------------------|
| `@类型:`     | 内容类型                    | `@类型: 标准操作流程(SOP)`                  |
| `@目的:`     | 目的说明                    | `@目的: 快速理解 skill 的核心价值`          |
| `@优先级:`   | 步骤优先级（必须/可选）    | `@优先级: 必须`                              |
| `@依赖:`     | 步骤依赖（引用步骤号/ID）  | `@依赖: step-locate-dash-root`              |
| `@改动文件:` | 修改/新增文件范围           | `@改动文件: ${DASH_ROOT}/source/pages/**`   |
| `@产物:`     | 输出物（文件/配置项）       | `@产物: ${DASH_ROOT}/source/pages/x_page.py`|
| `@文件:`     | 主要涉及的文件路径         | `@文件: ${DASH_ROOT}/source/pages/`         |
| `@路径:`     | 路径说明（目录级）         | `@路径: ${DASH_ROOT}/source/pages/`         |
| `@预期输出:` | 命令或操作的可观测输出      | `@预期输出: 输出包含 "created"`             |
| `@成功判定:` | 如何判断成功（最好可自动）  | `@成功判定: 退出码=0 且文件存在`            |
| `@失败信号:` | 如何判断失败/需要中止        | `@失败信号: 退出码!=0 或出现 Traceback`     |
| `@排查:`     | 最短排查路径（失败时用）     | `@排查: 检查路径变量与依赖步骤是否完成`     |
| `@回滚:`     | 恢复到安全状态的方法         | `@回滚: 删除本步骤新增文件并恢复配置`       |
| `@命令类型:` | 命令分类                   | `@命令类型: 脚手架`                           |
| `@用途:`     | 命令用途说明               | `@用途: 创建基础页面文件`                    |
| `@检索目标:` | 检索目标说明               | `@检索目标: 查 fac 组件 props`              |

**推荐注释字段顺序：**

- 工作流级：`@类型 → @目的 → @场景 → @前置条件 → @后置验证 → @触发条件 → @ID`
- 步骤级：`@类型 → @优先级 → @依赖 → @改动文件/@产物 → @验证点/@验证方式 → @文件/@路径 → @ID`

|----------------|------------------|--------------------------------------------------|

| `@后置验证:`   | 使用完后的验收   | `@后置验证: 页面可正常访问，日志无异常`         |

| `@触发条件:`   | 何种需求下触发   | `@触发条件: 当用户提出“新增页面/路由”需求时`    |
| `@类型:`       | 内容类型         | `@类型: 标准操作流程(SOP)`                      |
| `@目的:`       | 目的说明         | `@目的: 规范 SKILL.md 的语义化写法`             |

## 6. 变量系统

### 6.1 目录变量

使用 `${VAR_NAME}` 格式定义可替换变量：

| 变量           | 说明             | 示例值                             |
|----------------|------------------|------------------------------------|
| `${DASH_ROOT}` | Dash 项目根目录 | `server/`、`apps/web/server/` 等   |

### 6.2 变量使用规范

1. **首次出现需说明**：在文档开头明确 `${DASH_ROOT}` 的含义和可能的取值
2. **提供定位方法**：说明如何在仓库中确定 `${DASH_ROOT}` 的实际路径
3. **统一替换**：全文统一使用 `${DASH_ROOT}`，避免混用硬编码路径

## 7. HTML 注释元数据规范

推荐在每个工作流/步骤标题下方，用 HTML 注释记录元数据：

```markdown
### @步骤1: 创建页面模块

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @依赖: step-locate-dash-root -->
<!-- @验证点: 页面模块文件已创建 -->
<!-- @验证方式: 检查 ${DASH_ROOT}/source/pages 是否存在新文件 -->
<!-- @文件: ${DASH_ROOT}/source/pages/ -->
<!-- @ID: step-create-page-module -->
```

规范要求：

1. 注释紧贴在标题下方，中间不插入其他内容
2. 每个元数据一行 `<!-- @键: 值 -->`
3. `@ID` 在同一文档内唯一，便于 `@跳转到` 精确定位
4. 多值字段优先采用“重复键多行”的形式表达（便于机器解析），例如：
   - `<!-- @依赖: step-a -->` + `<!-- @依赖: step-b -->`
   - `<!-- @改动文件: path-a -->` + `<!-- @改动文件: path-b -->`

## 8. 解析优先级与冲突处理（推荐）

为提升 AI 执行一致性，推荐采用以下解析优先级：

1. **标题下方紧贴的 HTML 注释元数据**：作为机器解析的单一事实来源
2. **正文中的行内字段（如 `@工具:`、`@命令类型:`）**：用于展示与补充，但不应与元数据冲突
3. **纯自然语言说明**：仅作为背景信息，不参与执行决策

冲突处理建议：

- 若同一键在元数据与正文同时出现且值不一致，以元数据为准
- 若同一键在元数据中出现多次，视为多值集合（按出现顺序）
- 若关键必填字段缺失（见第 9 节），执行器应将该步骤标记为“不可执行/需补全”

## 9. 字段约束（必填/可选）

为降低不同作者的写法差异带来的执行不稳定，建议对常见节点类型定义最小字段集合。

### 9.1 工作流（`## @工作流`）

- 必填：`@类型`、`@目的`、`@场景`、`@前置条件`、`@后置验证`、`@触发条件`、`@ID`
- 可选：`@范围`、`@入口`、`@注意/@警告/@提示/@说明`

### 9.2 操作步骤（`### @步骤N` 且 `@类型: 操作步骤`）

- 必填：`@类型`、`@优先级`、`@ID`、`@验证点`、`@验证方式`
- 强烈建议：`@依赖`、`@改动文件`、`@产物`
- 可选：`@文件/@路径`、`@注意/@警告/@提示/@说明`、`@失败信号/@排查/@回滚`

### 9.3 验证步骤（`@类型: 验证步骤`）

- 必填：`@类型`、`@优先级`、`@ID`、`@验证点`、`@验证方式`
- 可选：`@依赖`、`@注意/@提示`、`@失败信号/@排查`

### 9.4 命令块（代码块附近的 `@命令类型/@用途/@路径` 等）

- 必填：`@命令类型`、`@用途`、`@路径`
- 强烈建议：`@成功判定`、`@失败信号`
- 可选：`@预期输出`、`@排查`、`@回滚`

## 10. 示例：完整工作流章节（推荐写法）

```markdown
## @工作流: 新增 core 页面

<!-- @类型: 标准操作流程(SOP) -->
<!-- @目的: 在 core 区域新增一个需要登录权限的页面 -->
<!-- @场景: 新增/修改 core 页面 -->
<!-- @前置条件: 已正确定位 ${DASH_ROOT} -->
<!-- @后置验证: 新页面可正常访问，菜单显示正确，权限规则生效 -->
<!-- @触发条件: 当用户提出“新增 core 页面”需求时 -->
<!-- @产物: ${DASH_ROOT}/source/pages/<业务域>/<页面名>_page.py -->
<!-- @产物: ${DASH_ROOT}/source/configs/router_config.py -->
<!-- @产物: ${DASH_ROOT}/source/pages/layout/layout_sidemenu.py -->
<!-- @产物: ${DASH_ROOT}/source/configs/auth_config.py -->
<!-- @ID: wf-add-core-page -->

### @步骤0: 确定 Dash 项目根目录

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @说明: 在多端/monorepo 项目中，需要先确定 Dash 应用所在子目录 -->
<!-- @验证点: 已唯一确定 ${DASH_ROOT} -->
<!-- @验证方式: 人工确认包含 server.py/app.py/router_config.py 的目录 -->
<!-- @失败信号: 无法唯一确定包含关键文件的目录 -->
<!-- @排查: 在仓库内全局搜索 server.py/router_config.py 并对比目录结构 -->
<!-- @ID: step-locate-dash-root -->

- @动作: 搜索包含 `server.py`、`app.py`、`router_config.py` 的目录
- @动作: 确认 `${DASH_ROOT}` 的具体路径（如 `server/`、`apps/web/server/` 等）
- @提示: 以下所有路径均相对于 `${DASH_ROOT}` 描述

### @步骤1: 创建页面模块

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @依赖: step-locate-dash-root -->
<!-- @改动文件: ${DASH_ROOT}/source/pages/<业务域>/<页面名>_page.py -->
<!-- @产物: ${DASH_ROOT}/source/pages/<业务域>/<页面名>_page.py -->
<!-- @文件: ${DASH_ROOT}/source/pages/ -->
<!-- @验证点: 新页面的 *_page.py 文件存在且可导入 -->
<!-- @验证方式: 检查文件存在，运行基础代码检查任务 -->
<!-- @失败信号: 文件无法导入或基础代码检查失败 -->
<!-- @排查: 检查文件命名、import 路径与依赖包是否存在 -->
<!-- @ID: step-create-page-module -->

- @动作: 在 `${DASH_ROOT}/source/pages/<业务域>/` 下创建 `<页面名>_page.py`
- @动作: 提供 `render_<页面名>_page()`，返回 Dash 组件树
- @说明: 页面结构推荐 `fac.AntdSpace(direction="vertical") + fac.AntdBreadcrumb(...)`

@工具: 使用脚手架脚本快速创建基础页面文件：

```bash
@命令类型: 脚手架
@用途: 创建基础页面文件
@路径: ${DASH_ROOT}/source/pages/
@成功判定: 退出码=0 且目标文件存在
@失败信号: 退出码!=0 或输出包含 Traceback
@排查: 检查 --page/--title 参数与 ${DASH_ROOT} 是否正确
python .trae/skills/kz-dash-developer/scripts/scaffold_page.py --page slug_name --title "页面标题" --apply
```

### @步骤2: 注册路由标题

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @依赖: step-create-page-module -->
<!-- @改动文件: ${DASH_ROOT}/source/configs/router_config.py -->
<!-- @文件: ${DASH_ROOT}/source/configs/router_config.py -->
<!-- @验证点: pathname → 标题映射存在 -->
<!-- @验证方式: 查阅 RouterConfig.valid_pathnames 配置 -->
<!-- @ID: step-register-pathname -->

- @动作: 在 `RouterConfig.valid_pathnames` 中注册 pathname → 标题映射
- @注意: 如需侧边菜单入口，保证 pathname 与菜单项 `href`/`key` 完全一致

### @步骤3: 配置 core_router

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @依赖: step-register-pathname -->
<!-- @改动文件: ${DASH_ROOT}/source/pages/layout/layout_sidemenu.py -->
<!-- @文件: ${DASH_ROOT}/source/pages/layout/layout_sidemenu.py -->
<!-- @验证点: 新 pathname 能被 core_router 正确识别并渲染 -->
<!-- @验证方式: 访问 URL，检查是否命中对应分支 -->
<!-- @ID: step-config-core-router -->

- @动作: 在 `core_router()` 中新增对应 pathname 的分支，调用 `render_<页面名>_page()`
- @动作: 在文件顶部按既有风格补充 import

### @步骤4: 权限规则

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @依赖: step-config-core-router -->
<!-- @改动文件: ${DASH_ROOT}/source/configs/auth_config.py -->
<!-- @文件: ${DASH_ROOT}/source/configs/auth_config.py -->
<!-- @验证点: 拥有权限的角色可访问，新角色访问行为符合预期 -->
<!-- @验证方式: 使用不同角色登录访问该 pathname -->
<!-- @ID: step-config-auth-rules -->

- @动作: 在权限配置中纳入新 pathname 的访问规则
- @警告: 若未配置，新页面可能被重定向到 403

### @步骤5: 整体验收

<!-- @类型: 验证步骤 -->
<!-- @优先级: 必须 -->
<!-- @依赖: step-config-auth-rules -->
<!-- @验证点: 页面访问与菜单状态正常 -->
<!-- @验证方式: 手动访问 URL，观察路由与菜单表现 -->
<!-- @ID: step-final-check -->

- @动作: 以 URL 直接访问新 pathname
- @动作: 检查是否命中 core_router 正确渲染内容
- @动作: 检查侧边菜单选中态与展开状态是否正确
