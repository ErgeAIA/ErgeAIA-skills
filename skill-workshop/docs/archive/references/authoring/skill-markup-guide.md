# Skill 语义化标记系统规范


> **一句话**: 语义化标记系统的完整规范参考
> **版本**: v1.4.0

## 触发示例

- "如何编写 SKILL.md 的语义化标记？"
- "和 @步骤 有什么区别？"
- "验证点应该怎么写？"

## 概述

本文档定义了目标 Skill 的 SKILL.md 文件的语义化标记系统，目标是：

- 为 AI 提供稳定、统一、可解析的结构化标记
- 降低 AI 从自然语言中“猜意图”的成本，提升 SOP 执行可靠性
- 支持多项目、多目录结构（单仓 / monorepo）之间的迁移复用

---

## 适用范围与豁免

本标记系统**仅对构建者类技能强制**。分类由 V0 校验器（`quick_validate.py`）自动判定：

- **构建者类**：SKILL.md 含 `` 头（即经 skill-workshop 脚手架创建、其 `@` 标记被 `generate_scenario_templates.py` / `quick_validate.py` 工具链解析消费）。必须完整使用 ``/`step N`/``/`` 等标记。
- **运行型（豁免）**：SKILL.md 无 `` 头、且工具链中无任何脚本消费其 `@` 标记（典型如纯指令型运行技能）。此类技能仅作为 LLM 运行时提示词，**强制 `@` 标记不产生任何运行时价值**（无消费者解析），反而增加 token 成本与虚假精度噪音，故按第一性原理豁免，V0 不再对其报 FAIL。

> 维护约定：若未来某运行型技能被新增工具脚本消费其 `@` 标记，它即转为构建者类，恢复强制——判定以"有无消费者"为准，而非技能主观分类。

---

## 标记系统总览

所有语义化标记使用 `@` 前缀，统一格式为：

- 行内字段：`@标记名: 值`
- 标题字段：`##  名称`、`###  标题`
- 注释元数据：``（仅供机器读取，不影响渲染）

标记按用途分为：结构标记、动作标记、范围标记、信息标记、元数据标记、文档标记。

为降低歧义并提升可执行性，建议在同一工作流/步骤内遵循“单一事实来源 + 明确优先级”的解析规则（见第 8 节）。

---

## 1. 结构标记

结构标记用于描述「工作流 → 步骤 → 子步骤」的层级结构。

| 标记       | 用途                     | 示例                           |
|------------|--------------------------|--------------------------------|
| `` | 定义标准操作流程(SOP)   | `##  新增 core 页面`   |
| ``  | 前置准备步骤（统一用 0） | `###  确定项目根目录`   |
| ``  | 正式执行步骤（1,2,3…）   | `###  创建页面模块`     |
| ``  | 后续执行步骤（依次递增） | `###  注册路由标题`     |
| ``     | 机器友好 ID（注释中给出）| `` |
| `@依赖:`   | 步骤对其他步骤/ID 的依赖 | `` |
| `@跳转到:` | 决策树/分支跳转到某个 ID | `@跳转到: step-create-page`    |

**规范：**

- 工作流标题统一：`##  名称`
- 步骤标题统一：`###  ...`、`###  ...`、`###  ...`
- 建议每个工作流与关键步骤都在注释中定义唯一 ``，供 `@跳转到` 精确引用
- `` 命名建议使用 `kebab-case`（仅小写字母/数字/短横线），并使用前缀区分层级：
  - 工作流：`wf-...`
  - 步骤：`step-...`
  - 决策/分支：`br-...`

---

## 2. 动作、产物与验证标记

动作标记用于标明“真正需要执行的操作”，验证标记用于说明“要验证什么、如何验证”。

| 标记         | 用途                           | 示例                                             |
|--------------|--------------------------------|--------------------------------------------------|
| ``     | 需要执行的具体操作            | `- 在 xxx 下创建文件`                     |
| `@改动文件:` | 本步骤会修改/新增的文件范围   | `@改动文件: ${DASH_ROOT}/source/pages/**`        |
| `@产物:`     | 本步骤输出物（文件/配置项）   | `@产物: ${DASH_ROOT}/source/pages/a/b_page.py`   |
| ``   | 要验证的结果 / 状态（what）   | `页面可正常访问，菜单显示正确`         |
| `` | 验证方法 / 手段（how）        | `手动访问 URL，检查返回状态码`       |
| `` | 整个工作流结束后的验收标准    | `新增页面可访问且权限规则正确`       |

**规范：**

- 在步骤正文中，所有可执行操作统一写成列表项：`- ...`
- 验证相关字段分工：
  - 步骤级：使用 `` + `` 描述
  - 工作流级：使用 `` 描述整体验收标准
- 如需可选动作，可用自然语言说明：`- (可选): ...` 或在步骤上用 `可选`
- `@改动文件` 与 `@产物` 优先写在标题下的 HTML 注释元数据中，减少正文与元数据重复带来的冲突

---

## 3. 范围与信息标记

这些标记为 AI 提供上下文、适用范围和辅助信息，用于“是否选择该 Skill / 工作流”。

| 标记       | 用途                         | 示例                                                 |
|------------|------------------------------|------------------------------------------------------|
| ``   | 适用场景描述                 | `新增/修改页面与回调`                         |
| `@范围:`   | 适用范围（页面级 / 项目级） | `@范围: 页面级复用`                                  |
| `@入口:`   | 关键文件索引                 | `@入口: 应用装配 → ${DASH_ROOT}/source/server.py`   |
| `@注意:`   | 执行相关注意事项 / 风险点   | `@注意: 如需侧边菜单入口，需同步配置菜单映射`       |
| `@警告:`   | 严重风险、错误后果           | `@警告: 若未配置权限规则会被重定向到 403`           |
| `@提示:`   | 执行时的操作性提示           | `@提示: 以下所有路径均相对于 ${DASH_ROOT} 描述`     |
| `@说明:`   | 背景说明 / 设计原因          | `@说明: 在多端/monorepo 项目中需要先定位 Dash 子目录`|
| `@工具:`   | 工具/脚本说明                | `@工具: 使用脚手架脚本创建基础页面文件`             |

**约定：**

- `@提示:` 面向“怎么做更顺手/少踩坑”
- `@说明:` 面向“为什么要这么做/背景原因”

---

## 4. 元数据标记

元数据标记主要出现在 HTML 注释中，方便 AI 抽取整齐的键值对。

| 标记         | 用途                        | 示例                                         |
|--------------|-----------------------------|----------------------------------------------|
| ``     | 内容类型                    | `标准操作流程(SOP)`                  |
| ``     | 目的说明                    | `快速理解 skill 的核心价值`          |
| ``   | 步骤优先级（必须/可选）    | `必须`                              |
| `@依赖:`     | 步骤依赖（引用步骤号/ID）  | `@依赖: step-locate-dash-root`              |
| `@改动文件:` | 修改/新增文件范围           | `@改动文件: ${DASH_ROOT}/source/pages/**`   |
| `@产物:`     | 输出物（文件/配置项）       | `@产物: ${DASH_ROOT}/source/pages/x_page.py`|
| `@文件:`     | 主要涉及的文件路径         | `@文件: ${DASH_ROOT}/source/pages/`         |
| `@路径:`     | 路径说明（目录级）         | `@路径: ${DASH_ROOT}/source/pages/`         |
| `@预期输出:` | 命令或操作的可观测输出      | `@预期输出: 输出包含 "created"`             |
| `@成功判定:` | 如何判断成功（最好可自动）  | `@成功判定: 退出码=0 且文件存在`            |
| `@失败信号:` | 如何判断失败/需要中止        | `@失败信号: 退出码!=0 或出现 Traceback`     |
| `@排查:`     | 最短排查路径（失败时用）     | `@排查: 检查路径变量与依赖步骤是否完成`     |
| `@回滚:`     | 恢复到安全状态的方法         | `@回滚: 删除本步骤新增文件并恢复配置`       |
| `@命令类型:` | 命令分类                   | `@命令类型: 脚手架`                           |
| `@用途:`     | 命令用途说明               | `@用途: 创建基础页面文件`                    |
| `@检索目标:` | 检索目标说明               | `@检索目标: 查 fac 组件 props`              |

**推荐注释字段顺序：**

- 工作流级：`→ → → → → @触发条件 → `
- 步骤级：`→ → @依赖 → @改动文件/@产物 → /→ @文件/@路径 → `

## 5. 文档标记

文档标记用于描述整个 Skill/SOP 文档自身的元信息。

| 标记           | 用途             | 示例                                             |
|----------------|------------------|--------------------------------------------------|
| ``   | 使用前的条件     | `用户已在本地拉取项目代码`           |
| ``   | 使用完后的验收   | `页面可正常访问，日志无异常`         |
| `@用法:`       | 文档使用方式     | `@用法: 根据用户需求匹配对应工作流执行`         |
| `@触发条件:`   | 何种需求下触发   | `@触发条件: 当用户提出“新增页面/路由”需求时`    |
| ``       | 内容类型         | `标准操作流程(SOP)`                      |
| ``       | 目的说明         | `规范 SKILL.md 的语义化写法`             |

## 6. 变量系统

### 6.1 目录变量

使用 `${VAR_NAME}` 格式定义可替换变量：

| 变量           | 说明             | 示例值                             |
|----------------|------------------|------------------------------------|
| `${DASH_ROOT}` | Dash 项目根目录 | `server/`、`apps/web/server/` 等   |

### 6.2 变量使用规范

1. **首次出现需说明**：在文档开头明确 `${DASH_ROOT}` 的含义和可能的取值
2. **提供定位方法**：说明如何在仓库中确定 `${DASH_ROOT}` 的实际路径
3. **统一替换**：全文统一使用 `${DASH_ROOT}`，避免混用硬编码路径

## 7. HTML 注释元数据规范

推荐在每个工作流/步骤标题下方，用 HTML 注释记录元数据：

```markdown
### 创建页面模块

```

规范要求：

1. 注释紧贴在标题下方，中间不插入其他内容
2. 每个元数据一行 ``
3. `` 在同一文档内唯一，便于 `@跳转到` 精确定位
4. 多值字段优先采用“重复键多行”的形式表达（便于机器解析），例如：
   - `` + ``
   - `` + ``

## 8. 解析优先级与冲突处理（推荐）

为提升 AI 执行一致性，推荐采用以下解析优先级：

1. **标题下方紧贴的 HTML 注释元数据**：作为机器解析的单一事实来源
2. **正文中的行内字段（如 `@工具:`、`@命令类型:`）**：用于展示与补充，但不应与元数据冲突
3. **纯自然语言说明**：仅作为背景信息，不参与执行决策

冲突处理建议：

- 若同一键在元数据与正文同时出现且值不一致，以元数据为准
- 若同一键在元数据中出现多次，视为多值集合（按出现顺序）
- 若关键必填字段缺失（见第 9 节），执行器应将该步骤标记为“不可执行/需补全”

---

## 9. 字段约束（必填/可选）

为降低不同作者的写法差异带来的执行不稳定，建议对常见节点类型定义最小字段集合。

### 9.1 工作流（`## `）

- 必填：``、``、``、``、``、`@触发条件`、``
- 可选：`@范围`、`@入口`、`@注意/@警告/@提示/@说明`

### 9.2 操作步骤（`### step N` 且 `操作步骤`）

- 必填：``、``、``、``、``
- 强烈建议：`@依赖`、`@改动文件`、`@产物`
- 可选：`@文件/@路径`、`@注意/@警告/@提示/@说明`、`@失败信号/@排查/@回滚`

### 9.3 验证步骤（`验证步骤`）

- 必填：``、``、``、``、``
- 可选：`@依赖`、`@注意/@提示`、`@失败信号/@排查`

### 9.4 命令块（代码块附近的 `@命令类型/@用途/@路径` 等）

- 必填：`@命令类型`、`@用途`、`@路径`
- 强烈建议：`@成功判定`、`@失败信号`
- 可选：`@预期输出`、`@排查`、`@回滚`

## 10. 示例：最小可用工作流章节（推荐写法）

> 示例只示范**全部必填标记的形态**（工作流头 / 步骤头 / HTML 注释元数据 / / 验证五件套 / 命令块）。真实工作流按业务需要增加步骤，不必模仿示例的领域内容。

```markdown
## 新增 core 页面


### 确定 Dash 项目根目录


- 搜索包含 `server.py`、`app.py`、`router_config.py` 的目录
- 确认 `${DASH_ROOT}` 的具体路径（如 `server/`、`apps/web/server/` 等）
- 以下所有路径均相对于 `${DASH_ROOT}` 描述

### 创建页面模块


- 在 `${DASH_ROOT}/source/pages/<业务域>/` 下创建 `<页面名>_page.py`
- 提供 `render_<页面名>_page()`，返回 Dash 组件树


```bash
python scripts/scaffold_page.py --page slug_name --title "页面标题" --apply
```
```
