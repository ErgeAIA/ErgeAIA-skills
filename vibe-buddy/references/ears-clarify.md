# req · EARS 需求澄清（薄）

## 目的

把「加个导出」「登录要记住我」这类口语需求，变成**每条都能判定通过与否**的条目。产出给谁看都行：人、grilling（接着追问）、qiao（编译成任务）。

**本技能不落盘**（`writes-to` 为空）。用户明确要文件才写，路径由用户指定。

## 内核：升维四问（EARS 之前先跑）

本技能的精髓不是 EARS 语法，而是这四问——**要更深，不是更大**。在归类之前先问自己：

| # | 问什么 | 落到需求上 |
|---|---|---|
| 1 | 这个领域的顶尖高手会做而用户**没要求**的是什么？ | 找出缺口：用户说「导出 CSV」，高手还会问「失败重试 / 空数据 / 权限」——这些是 U* 条目 |
| 2 | 高手会从什么**最原始的材料**开始，而不是别人消化过的？ | 找事实源：用户说「按上次的规则」，原始材料是代码/配置/数据本身，不是会话里的转述 |
| 3 | 他们会用哪些**具体方法与工具**？ | 找可测手段：不写「要快」，写「用 X 实测 N 秒内完成」 |
| 4 | 除了你和用户，**还有什么**能证明结果是对的？ | 找外部验证：日志 / 监控 / 测试 / 对账 / 第三方输出——不靠「我觉得可以」 |

四问的作用：把用户的浅层要求**抬到专业标准**，而不是把字数变多。产出是「更深的需求」，不是「更长的需求」。

**怎么用在归类前**：

- 四问的答案**不直接写进输出**（不是给用户的问卷）；它们决定哪些 EARS 条目该存在。
- 第 1 问的缺口 → 落成 U*（不期望型）条目。
- 第 2 问的原始材料 → 若缺失，写进「待确认」，不拿转述当事实。
- 第 3 问的方法 → 决定 `<响应>` 是否具体（能测才写）。
- 第 4 问的外部验证 → 决定这条能不能判定通过；答不出就是「待确认」。

**边界**：四问是给自己升维用的，不是拿去追问用户。真正需要用户回答的问题仍走下面「澄清」一节（最多 3 问）。

## 为什么薄

参考的 CodeBuddy 命令 `/req-clarify` 有两处不适合直接搬：

1. **五节空表模板**：无条件列出 Ubiquitous / Event-Driven / State-Driven / Optional / Unwanted 五节再打勾，逼用户填不存在的条目——这是填空模板，不是判据。
2. **`!` 反引号注入**：自动 `cat package.json` / `find` 扫盘——这是命令执行，不是需求澄清；本技能默认不运行命令。

所以这里只取它的**语法模式**（五类句式），不取它的流程外壳。

## EARS 五类句式（唯一真源）

按「这条需求在什么条件下成立」归类，**一条只归一类**：

| 类 | 句式 | 判据（满足才用） |
|---|---|---|
| U Ubiquitous | 系统应 `<响应>` | 无条件成立，不依赖事件/状态/开关 |
| E Event-Driven | 当 `<触发器>` 时，系统应 `<响应>` | 由**一次性事件**触发（点击 / 提交 / 定时 / API 调用） |
| S State-Driven | 当 `<状态>` 时，系统应 `<响应>` | 由**持续状态**决定（离线 / 加载中 / 已登录） |
| O Optional | 在 `<特性激活>` 的情况下，系统应 `<响应>` | 有显式开关或配置（设置项 / 环境 / 灰度） |
| U* Unwanted | 如果 `<触发器>`，那么系统应 `<响应>` | 处理**不期望情况**（失败 / 越界 / 权限不足 / 超时） |

归类顺序：先判 U*（是不是在防坏事）→ 再判 E/S（触发器是一次事件还是持续状态）→ 再判 O（有没有开关）→ 剩下是 U。

**E 与 S 的判别**（最容易混）：问「条件结束了吗」——点击是一次事件（E）；「处于离线」是持续状态（S）。同一行为可写两条，但触发条件不同，就不是同一条。

## 每条必须可测试

写完逐条过三问，缺一不输出：

1. **触发可见吗**：`<触发器>` / `<状态>` / `<特性>` / `<不期望情况>` 能观测到吗？（「用户觉得合适时」不可观测 → 不通过）
2. **响应具体吗**：`<响应>` 是动作 + 对象，不是「处理 / 优化 / 支持」这类空动词。
3. **能判定通过吗**：看到系统和没看到系统，能区分这条满足与否吗？不能 → 改写或标「待确认」。

**不通过就改写到通过，或标「待确认」并说明缺什么**，不凑数、不写「系统应良好地工作」。

## 澄清：只问改变归类的问题

- 不问：优先级、排期、技术方案、UI 细节、边界数值（除非它决定归入 U*）。
- 只问：**答案会把条目归到不同类**或**让 `<响应>` 从不可测变可测**的问题。
- 一次最多 3 问，每个问题给推荐答案；用户答了就落条，不追第二轮。
- 能从上下文、项目文件、`AGENTS.md` 推断的，不问。

**追问超过 3 问仍有未知 → 转 `grilling`**：让它按 design tree 把决策问透，本技能拿着共识再归类。这是不重复轮子的关键——追问是它的活。

## 输出格式

只输出有内容的类，**空类不写**。每条一行：

```text
## EARS 需求 · <主题>

U 系统应 <响应>
E 当 <触发器> 时，系统应 <响应>
S 当 <状态> 时，系统应 <响应>
O 在 <开关> 激活的情况下，系统应 <响应>
U* 如果 <不期望情况>，那么系统应 <响应>

待确认：<一句话说缺什么，才不能落条；没有写「无」>
```

- 每条前缀 `U` / `E` / `S` / `O` / `U*` 不可省——它是分类证据，不是装饰。
- 不写「优先级 / MVP 分期 / 排期」：那是需求管理，不是 EARS。
- 不写「系统应使用 React」这类实现：EARS 描述做什么，不描述怎么做。

## 与其他技能的分界

| 场景 | 归谁 |
|---|---|
| 把口语想法变成**可验收需求条目** | **本技能（vibe-req）** |
| 无休止追问、把 plan/decision 问透、出 ADR / glossary | `grilling` / `grill-with-docs`（第三方，只读不修改） |
| 把需求压成给 Coding Agent 的**最小充分任务** | `qiao`（独立技能，不动） |
| 改写 / 优化 / 评估文本 Prompt | `prompt-workshop` |
| 写代码、重构、调试 | 开发技能 |

**组合顺序**：vibe-req（归类成条目）→ qiao（编译成任务）→ 开发技能。用户只要其中一段就只跑那一段，不自动串。

## 失败处理

| 触发条件 | 一线修复 | 仍失败兜底 |
|---|---|---|
| 用户要求「把需求写成文件」 | 先给 EARS 条目，问落盘路径 | 用户没给路径 → 只回话不落盘 |
| 需求本身就是 plan / decision 层级 | 停止归类，指向 `grilling` | 用户坚持 → 说明 EARS 只描述系统行为 |
| 3 问后仍无法归类 | 转 `grilling`，本技能暂停 | 共识回来再跑一次归类 |
| 目标含 `SKILL.md` 且要审技能质量 | 转 `skill-workshop` | — |
