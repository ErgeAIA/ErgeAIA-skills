# distill · 把开发过程蒸馏成可复用经验

## 目标

把**本项目开发过程中反复成立的做法**，从一次性的记录里提炼成**按主题组织的可复用经验**：让本项目下一次不必重踩，也让这些结论能离开本项目被复用。

**不蒸馏会话。** 原料是项目里已经沉淀的事实（决策、踩坑、代码现状、提交历史）；本次对话只是补充来源——会话会压缩、会丢，靠它蒸馏就是靠记忆写规则。

## 与 vibe-sync 的分界

| | 记录什么 | 落点 |
|---|---|---|
| `vibe-sync` | **发生了什么**（流水，只对本项目有意义） | `docs/.ai/project-progress.md`、`decision-log.md`、`debug-log.md` |
| `vibe-distill` | **什么事反复成立**（抽象，能带走） | `docs/.ai/experience/` |

判据一句话：**这条经验离开这个项目还成立吗？** 成立才值得蒸馏。

## 蒸馏的单位是「一轮」

一轮 = 一次集中的开发活动（一个重构轮、一次性能优化、一个发布准备、一轮界面整改）。**不是一次会话**——一轮常跨多个会话。

## 事实源

| 序 | 事实源 | 取什么 |
| -- | ------ | ------ |
| 1 | `git log --oneline -n <N>`、`git status --short`、`git diff --stat` | 本轮改了哪些提交、涉及哪些文件；**仅本项目在 Git 仓库内时可用** |
| 2 | `docs/.ai/decision-log.md` | 本轮相关决策（`DEC-NNN`） |
| 3 | `docs/.ai/debug-log.md` | 本轮踩的坑与根因（`BUG-NNN`） |
| 4 | **代码实际形态**（`search_content` 统计） | 实测数字，如「15px 出现 255 处」「286 个按钮」 |
| 5 | 本次会话上下文 | 仅作补充；与 1–4 冲突时以客观源为准 |

- 条目里的数字（处数、文件数、覆盖数）必须**实测**，禁止按印象写
- 写「How」时给**可直接照抄的原文**：类名全文、命令原文、`文件:行号`
- 项目不是 Git 仓库 → 跳过第 1 项，不报错

## 准入判据（不满足就不入库）

1. **能离开本项目还成立** —— 否则它是项目参数，标 🟢 而非剔除
2. **写得出反例**（错误做法 + 后果）—— 写不出说明还没想清楚，不入库
3. **有事实源** —— 能指到 `DEC-NNN` / `BUG-NNN` / commit / 实测数字

不值得蒸馏的：一次就改好的笔误、环境偶发、纯偏好且说不出 Why 的、无法验证的。

## 分级 = 可移植性，不是重要性

| 级 | 含义 | 换项目时 |
|---|---|---|
| 🔴 红线 | 任何技术栈、任何项目都成立的立场 | 照搬 |
| 🟡 倾向 | 风格偏好，有 Why 支撑 | 按语境采纳 |
| 🟢 参数 | 具体数值、主题、尺寸，只对本项目成立 | **必须替换，禁止盲抄** |

## 条目格式（五要素，缺一不可）

````markdown
## 🔴 R13 — <一句话标题>

- **主张**：
- **适用**：<什么前提下成立；换项目能否迁移>
- **Why**：
- **How**：<可直接照抄的原文 / 命令 / 文件:行号>
- **反例**：<错误写法 + 后果>
````

- 编号在**主题内**递增：`R#` 红线 / `T#` 倾向 / `G#` 参数
- 「适用」必须写：它同时决定「与本项目旧条目是否真冲突」和「拿出去复用时是否成立」
- 「反例」不是可选段：外送汇总时它会派生成一张独立的反模式卡

## 落盘结构

````text
<project>/docs/.ai/experience/
├── README.md       # 总索引 + 适用范围 + 使用步骤 + 🔴 速查 + 外送前置条件
├── changelog.md    # 兼台账：每轮「原料区间 + 覆盖主题 + 产出 + 事实源」
└── <域>/           # 主题 = 领域名，一域一目录
    ├── README.md   # 域内索引（该域条目清单）
    └── *.md        # 分章
````

- **主题名用领域名**，不另造词：`ui`、`frontend`、`motion`、`backend`、`database`、`security`、`architecture`、`performance`、`testing`、`devops`
- `README.md` 与 `changelog.md` 首次蒸馏时按 `assets/experience/` 同名模板创建，只换 `<域标识>` / `<工程标识>` 与 `updated`；域目录与分章按内容自建
- 单章超过约 250 行（含空行的总行数，实测）时拆为同域下的多个文件

## 写入规则

- **正文可改写，历史靠 changelog**：与 `docs/.ai/` 的「只追加」不同——错的规则留在正文会持续误导。修订时改写条目本身，并在 `changelog.md` 记「旧结论 → 新结论 + 为什么」
- 只改本轮事实支持的部分，不顺手重排、不顺手改无关条目
- `README.md` 的 🔴 速查与主题索引随条目增删同步
- 改完把各文件 frontmatter 的 `updated` 改为当日

## 防重复蒸馏

写任何条目之前**先读 `changelog.md`**，比对本轮原料区间是否与已记录区间重叠：

- 完全重叠 → 停下告诉用户「这段已在 <日期> 的 <轮次> 蒸馏过」，不重复蒸
- 部分重叠 → 只蒸新增部分，并在备注里说明

`changelog.md` 一条的格式：

````markdown
## YYYY-MM-DD · <轮次主题>

- **原料**：`<首个commit>..<末个commit>` · `DEC-NNN` · `BUG-NNN`
- **覆盖主题**：
- **产出**：新增 T16；T12 扩展；新增 R13
- **有意跳过**：<无 / 原因>
````

## 冲突怎么处置（不裁决）

发现新提法与既有条目矛盾时，**先比适用条件，再比结论**：

| 情况 | 判据 | 处置 |
|---|---|---|
| 前提不同（项目背景不同） | 适用条件不一样 | **不是冲突**。两条并存，各自标注适用条件 |
| 同一前提下结论矛盾 | 适用条件相同 | **真冲突** → 停下问用户，不自行取舍 |

**不自动裁决**——语义冲突本就该人判。用户裁决后，才按「正文可改写 + changelog 留痕」执行。

## 什么不写

- **不写 `docs/.ai/` 的进度、决策、调试三份**：那是 `vibe-sync` 的记录区。本条若还只是流水事实，先提示跑 `vibe-sync`
- **不写 `docs/.ai/agents-changelog.md`**：AGENTS.md 契约改动记录，`vibe-init` 独占
- **不写入任何外部仓库或目录**：本技能只在项目内产出基料，外送由用户另行触发
- **不把项目名、绝对路径、账号写进条目**：条目要能离开本项目

## 终止回复

三行：本轮覆盖的主题与「新增 / 修订」条目数；`experience/` 落盘路径；未决的冲突或待确认项（无则写「无」）。

若有条目应上升为项目级规则，追加一句建议走 `vibe-init` 增量维护写入 `AGENTS.md`。
