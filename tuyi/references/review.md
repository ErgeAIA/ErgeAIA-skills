# 审查

审查不是「看着不顺眼就提意见」，而是**拿规则比对实现，每条结论都能指到文件和行**。

## 输入分级

先判手里有什么，能查到什么程度，再决定结论的强度：

| 输入 | 能查 | 结论强度 |
| --- | --- | --- |
| 源码 + 样式（.tsx/.css） | 结构、类名、内联样式、令牌、import 来源 | 最强，可跑机器检查到 `file:line` |
| DOM 快照 / 渲染后 HTML | 结构、class、aria 属性、内联样式 | 中，样式规则需回查 CSS |
| 截图 / 设计稿 | 视觉形态、尺寸、颜色、间距 | 弱，只能人判，必须标注「未验证样式来源」 |
| 口头描述 | 几乎没有 | 不算审查，转为需求澄清 |

拿不到源码时**不要假装能验证样式**：结论写「目测疑似 + 需要看源码确认」，这是证据纪律，不是保守。

## 三步

### 1. 取规则

读 profile：槽位定义、locked 映射、条款（`check` + `source_ref` + `severity` + `fix`）、`conflicts`。

没有 profile 时先走 `profile.md` 的「轻量抽取」，产出一份 draft，并明确告诉用户：**规则是从现有实现反推的，所以「一致性」可查，「正确性」需要规范确认**。

### 2. 机器检查

```bash
PYTHONIOENCODING=utf-8 uv run --no-project python scripts/badge_lint.py --profile profile.yaml --target src/ --format json --out findings.json
```

机器查的是**形态**：有没有边框、尺寸是不是允许值、有没有 aria-label、数字有没有塞进图标、热区够不够、有没有直接 import 图标库、图标旁是否挂了字。

覆盖口径（`badge_lint.py` 1.1.0 起）：

- 开标签按字符级状态机跨行解析，属性跨行、自闭合、字符串/表达式/泛型里的 `>` 都按整体归属到同一元素
- CSS 规则块与内联 `style`（JSX 对象、HTML 字符串）走同一套判定；内联命中同样给 `file:line` 与规则 id
- 解析失败或取值无法静态判定的规则进入 `unchecked`（JSON 里是 `unchecked` / `summary.rules_unchecked` / `summary.unchecked_items`，text 报告有「未检查」节），**不计入 `passed`**；`N/A` 只表示「目标中没有相关元素」，两者不混用

### 3. 人判

机器查不出**语义**，这部分必须人工（也就是你）判断：

1. **槽位错配**：状态位放了动作图标，来源位放了判定图标
2. **借用错误语义**：字面义污染了正常状态（`unlink` 当「本地」）
3. **同排混淆**：同行图标 16px 剪影相近，扫视时分不清
4. **图文重复**：图标旁又挂了一句同义文字（等于两套编码，白占宽度）
5. **Tooltip 失真**：缺失、与语义不符、或承载了必须常显的信息
6. **判定色滥用**：正常状态用警示色，或同排多个元素都在用状态色
7. **层级塌陷**：来源图标和状态图标同尺寸同色，抢同一层注意力

每条人判也要落到 `file:line` 或「选择器/组件名」，不能停在「整体感觉乱」。

### 动效审查（9 项）

`badge_lint.py` 只查静态选择器、属性与期望值，**不检查运行时生命周期、语义必要性或任务结束后是否停止**。以下全部是 `human_check`，判据见 `motion.md`：

1. 是否把动作误做成状态动画，或把状态误做成动作
2. 是否对应真实状态、任务或操作反馈
3. 触发事件是否真实且唯一（不是加载即播、滚动触发、常驻）
4. 目标是否正确：整枚图标 / SVG 内部子路径 / 输入容器
5. 循环是否有终止条件
6. 完成、失败、取消、卸载时是否停止（`getAnimations()` 应无遗留循环）
7. 是否超项目预算：同屏主动画并发、连续动画数量、入场时长
8. 时长、缓动、次数是否来自项目令牌；裸毫秒是否被当成规则
9. reduce 是否真正降级（keyframes 要显式关闭，不能只把 transition 时长调小），静态时是否仍可理解

源码不足 → `N/A`；有源码但无法运行时验证 → `needs-review`，并在报告里写清缺什么环境或事件；不得只凭「源码里有 `prefers-reduced-motion`」判通过。

## 严重度

| 级别 | 判据 | 处置 |
| --- | --- | --- |
| **blocker** | 会直接导致误读或误操作（状态被读成动作、正常被读成故障） | 必须改，改前不放行 |
| **major** | 明确违反规范条款，但不改变语义（尺寸/边框/热区/缺 aria） | 本迭代内改 |
| **minor** | 一致性、可优化（同族图标风格不齐、Tooltip 措辞不统一） | 排期改 |

严重度只由「误读后果」决定，不由「改起来麻烦」决定。反过来也不行：不能因为改起来容易就升成 blocker。

## 误报控制

- **未覆盖 ≠ 通过**：目标里没有相关元素标 `N/A`；元素存在但解析失败/取值动态标 `unchecked`。两者都另列清单，都不算合规。
- **单点不外推**：只看到一个实例，不给「全站都是这样」的结论。
- **冲突不静默**：profile 里 `status: pending` 的条款，按 `interim` 值判，并在报告里点名「此项待规范所有者裁决」。
- **不确定就降级**：拿不准是规范违反还是设计选择，标 `needs-review` 并提出问题，不硬判。
- **不重复计数**：同一根因在 20 个文件出现，合并成一条，附完整 `file:line` 列表，避免报告被噪音淹没。

## 报告结构

按 `templates/review-report.md` 写，六节：

1. **审查范围与依据**：目标路径、profile 名称/版本/来源、跑了什么命令
2. **结论摘要**：blocker/major/minor 计数 + 一句话判断（能不能放行）
3. **findings**：表格，列为 `类别（形态/动效）` / `file:line` / 规则 id + 条款 / 现状 / 为什么错 / 最小改法 / 严重度；动效行补触发、停止、reduce 三个字段
4. **已合规清单**：明确查过且通过的项目（让人知道覆盖到哪）
5. **N/A、needs-review 与待裁决**：没覆盖到的、运行时未验证的、profile 里 pending 的
6. **优化建议排序**：先语义、再形态、最后一致性

## 优化建议的排序原则

按「修复收益 / 改动成本」排，但**语义错误永远排第一**，哪怕它只影响一个位置——因为语义错误会训练出错误的阅读习惯，改得越晚越贵。

第二层是形态违约（能一次性批量修完的集中修）。第三层才是一致性打磨，这一层要克制：不要为了「整齐」去改语义正确的东西。

## 自检

- 每条 finding 都有位置与条款号
- 没有把 N/A 写成「通过」
- pending 冲突已点名，没有替规范所有者裁决
- 建议里没有「换成我觉得更好的」这类无依据替换
- 已合规清单非空（否则说明覆盖不足）
- 动效结论没有把「建议」写成「项目规则」；pending 与 `needs-review` 已单列
- 运行时未验证的动效没有冒充通过；reduce 与停止条件有真实证据或明确缺口
