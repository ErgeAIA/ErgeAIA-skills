# 方法依据

本技能的维度划分与判分方式不是自创，取自当前公开基准里经过验证的做法。**但不用它们的原始题**——理由见末节。

## 数学推理 → GSM8K 一脉

| 项 | 内容 |
| --- | --- |
| 代表基准 | GSM8K（小学应用题）、MATH（竞赛题） |
| 判分机制 | 抽取最终数值，与标准答案精确比较；GSM8K 用 `#### <answer>` 标记最终值 |
| 本技能取用 | 最终值抽取（含 `####`、`\boxed{}` 两种标记）+ 数值容差比较 |
| 本技能不用 | 不要求 CoT（GSM8K 的 few-shot 链式示范），因为本地小模型的 CoT 质量本身不稳定，会污染「算得对不对」这个信号 |

**为什么加「信息不足」题**：GSM8K 全是可解题，模型养成了「必须算出数」的倾向。真实使用中，题目缺条件是常态，硬算出数是最危险的失败模式。所以专门设两题，正解是拒答。

## 指令遵循 → IFEval / IFBench 一脉

| 项 | 内容 |
| --- | --- |
| 代表基准 | IFEval（25 类可验证约束）、IFBench（58 类 held-out 约束） |
| 判分机制 | 每条约束一个 Python 验证函数，逐条 pass/fail；报 prompt-level 与 instruction-level 两个准确率 |
| 本技能取用 | 同一范式：约束 → 代码判定 → 部分得分 + 全通过率双口径 |
| 本技能不用 | 不直接跑 IFEval 题集——2025 年起 2B–8B 模型普遍 80%+，已饱和，测不出本地模型差异 |

**IFBench 的关键发现**（影响本题库设计）：模型会对有限的约束类型过拟合，换成未见过的约束就崩。所以本题库的约束是自写的，且刻意包含不常见组合（三行且每行恰好五字、答案本身是数字但禁阿拉伯数字）。

**IFBench 的已知局限**（也是本技能的局限）：只覆盖能用短 Python 函数验证的约束；「说得友好些」「别用术语」这类用户真实会提的要求无法验证，本技能明确不做。

## 事实性与幻觉 → SimpleQA / TruthfulQA 一脉

| 项 | 内容 |
| --- | --- |
| 代表基准 | SimpleQA（短事实问答，考校准）、TruthfulQA（对抗性误导问题） |
| 判分机制 | SimpleQA 三分：correct / incorrect / not attempted，并用置信度算校准；TruthfulQA 用微调的 GPT-judge 判真伪 |
| 本技能取用 | **三分类**（答对/答错/弃答）+ **置信度校准 ECE**；TruthfulQA 的「对抗性提问」思路用于设错误前提题 |
| 本技能不用 | 不用 GPT-judge——那是 LLM 裁判，破坏离线与可复现。TruthfulQA 的 judge 是在人工标注上微调的专用分类器，本地无法复现同等质量 |

**为什么三分类比二分类重要**：把「弃答」和「答错」混在一起，就分不清「模型保守」和「模型胡说」。这两个失败模式的处置完全不同——保守可以调提示词，胡说只能换模型或加 RAG。

**校准为什么要单独报**：SimpleQA 的核心贡献之一是指出「大模型普遍过度自信」。一个 90% 置信度但只有 60% 正确率的模型，比一个 60% 置信度 60% 正确率的模型危险得多。

## 工具调用 → BFCL 一脉

| 项 | 内容 |
| --- | --- |
| 代表基准 | BFCL（Berkeley Function Calling Leaderboard） |
| 判分机制 | 三代演进：① **AST 匹配**（把调用解析成语法树，比函数名 + 参数类型/值，与参数顺序无关）② **真实执行**（沙盒里跑，看状态是否真的改变）③ **多轮状态模拟**（上轮结果驱动下轮） |
| 本技能取用 | AST 匹配的思想：解析调用 → 结构化比对 → 顺序无关 → 类型敏感（`42` 与 `"42"` 需归一化处理） |
| 本技能不用 | 不做真实执行（需沙盒）与多轮状态模拟（需工具返回注入）。这两项在本地评测里成本过高，且需要 Docker 级隔离 |

**BFCL 的关键分类**（本题库照搬其任务类型）：simple（单函数）、multiple（多选一）、parallel（并行）、irrelevance（**该不调用时不调用**）。

**irrelevance 为什么单列**：BFCL 把「幻觉调用」当成独立能力维度，因为模型在无匹配工具时编造调用的危害，比选错工具更大——它会真的触发一个不存在的动作。本题库用三题专测（无翻译工具、只读工具要删表、无导入工具）。

**AST 匹配为什么优于字符串比对**：`{"a":1,"b":2}` 与 `{"b":2,"a":1}` 语义相同，字符串比对会误判为不同；`42`（int）与 `42.0`（float）在多数 API 里等价。本技能按此归一化。

## 为什么不用这些基准的原始题

三个理由，按严重度排序：

1. **污染**。GSM8K、MMLU、IFEval 都在主流训练数据里。模型可能记住了答案，分数虚高且无法察觉。
2. **饱和**。IFEval 在 2025 年已被 8B 模型刷到 80%+，对本地模型档位没有区分度。
3. **不可控**。原始题集动辄数千题，本地 16GB 显存跑 14B Q4 要几小时。私有小题库能在 20 分钟内给出可决策的信号。

**取舍**：私有题牺牲了「与公开榜单可比」，换来「能测出本地模型差异」与「跑得起」。若需要外部锚点，单独跑一次公开集子集作参照，但**不进总分**——口径不同不可混算。

## 还能怎么扩展

按成本从低到高：

| 扩展 | 成本 | 需要什么 |
| --- | --- | --- |
| 加题（同维） | 低 | 改 jsonl + selftest |
| 加约束类型 | 低 | 改 `scorers._check_constraint` + selftest 用例 |
| 多轮工具调用 | 中 | 需要工具返回注入循环 + 状态比对，参考 BFCL multi-turn 的 `possible_answer` 结构 |
| 代码执行验证 | 高 | 需要沙盒（Docker / firejail），参考 Inspect AI 的 sandbox 机制 |
| 长上下文检索 | 中 | 需要构造 needle-in-haystack 题，测的是上下文窗口而非推理 |
