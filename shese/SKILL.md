# 设色 · Shese

> 设色者，布色于位，明其阶次。先定其所用，再正其所失。

## 定位

在用户声明的阅读场景下，让一套配色读得舒服，同时不丢失它原本要表达的情绪；让不懂色彩学与设计的人也能拿到结论，并看见这套色在真实界面里的样子。

Core Task：

```text
声明阅读目标 → 还原语义角色 → 展开 alpha 合成 → 按机制判定 → 最小改动优化 → 出预览页与 token
```

两条轨道共用同一条判定链：

- **审查轨**：用户给既有配色（十六进制列表或语义 token）+ 场景 → 判定 + 最小改动优化。
- **生成轨**：用户给一句风格意图、症状词或参考锚点 → 2–3 套**结构不同**的候选（不是只换色相）→ 走同一条判定链逐套验一遍。

**唯一标准**：在指定阅读场景下阅读舒适性最高，同时不丢失配色原本要表达的情绪。审美偏好不得凌驾于可读性。结论先行，不做赞美式点评。

## 不可违背

1. **目标先行**：先声明阅读目标（用途、单次阅读时长、环境亮度、字号与字重、信息密度），再由目标反推尺度。禁止先拿通用数字去套场景。
2. **判据是机制，不是数字**：每条判定都要说明依据的视觉机制；数字只是该机制在常见场景下的默认刻度，不是门禁。
3. **判定三级标注**：硬底线（违反即不通过，只覆盖直接破坏阅读或造成误读的部分）／参考锚点（通用默认起点，可浮动，浮动须给理由）／目标推导（由第 1 条目标直接算出，不同目标必然得出不同结论）。
4. **建议优先于判定**：多数问题存在合理区间而非单一最优值——给区间 + 推荐点 + 取舍代价，把选择权交回用户；不以「通过 / 不通过」收尾。
5. **偏离要补偿**：任何偏离锚点的取值，都要说明它服务哪个目标、用什么补偿（提字号、加字重、拉开层级明度差、减小高彩度面积）。
6. **alpha 必须声明基准面**：带 alpha 的文字 token 要声明它允许出现的最差背景面，对比结论以该面上的合成实色为唯一依据；未声明基准面的数字视为无效。
7. **合成按浏览器口径**：在 sRGB 空间混合；多重叠加沿整条链计算（半透明文字落在半透明背景或 hover 叠加层上），不能只算一层。设计工具在线性空间混合时两端结果不一致，以浏览器渲染为准并注明口径。
8. **对比是双向约束**：上限与下限同样重要。深色模式正文避免纯白，浅色模式正文避免纯黑；极高对比会带来光晕与眩光，长阅读反而疲劳。
9. **文字结论必须绑定字号与字重**：小字号、细体属于高空间频率，需要更高对比补偿；大字号或粗体可略低。不给脱离字号的无条件合格判定。
10. **不擅自替换品牌色与主色相**：若它造成可读性问题，只指出并给替代用途。
11. **不为「更高级」引入新色相**：新增色值必须对应一个已存在的语义缺口。
12. **每条结论挂在具体色值与机制上**：不接受纯审美评价；深色与浅色分别审查，不用一套结论覆盖。
13. **语言与符号**：输出语言与输入一致；不用 emoji 与装饰性符号。

## 判定表（十项，逐项读出「等级 + 默认起点 + 依据机制」）

| 审查项 | 等级 | 默认起点与依据机制 |
| --- | --- | --- |
| 承载阅读的正文对比 | 硬底线 | 起步档按 APCA 官方字号—字重矩阵查表定（16px/400 需 Lc 90、24px/400 需 Lc 60、32px/400 需 Lc 50），不可脱离字号与字重给结论；相对亮度比仅作记账，不进判定。依据：对比度、空间频率、极性 |
| 次级 / 弱化文字 | 锚点 | 允许低于正文，但只用于短标签与辅助信息，不承载长句。依据：对比度、阅读负荷 |
| 文字 token 含 alpha | 硬底线 | 必须声明合成基准面，且在最差面上仍满足其角色的对比要求。依据：透明度与合成 |
| 层级明度差 | 锚点 | 相邻层级在 OKLCH 中拉开可辨差距即可，深色模式通常需要比浅色更大的间隔。依据：感知均匀空间、侧抑制 |
| 高彩度色的面积 | 锚点 | 点睛与品牌色保持较小面积，具体占比随界面密度调整；关键看是否与正文争夺注意力。依据：面积与彩度 |
| 大面积填充彩度 | 锚点 | 背景与卡片保持中等以下彩度。依据：面积与彩度 |
| 深浅模式基础色 | 硬底线 | 不用纯黑底与纯白正文；具体取值由阅读环境与时长决定。依据：暗适应、浦肯野效应、光晕 |
| 语义色可区分性 | 硬底线 | 状态色之间需同时具备明度或形态差异，不只靠色相。依据：色觉差异、冗余编码 |
| 色觉模拟校验 | 硬底线 | 三类模拟（protan / deutan / tritan）下正文仍可读、语义色仍可区分；任一失效即需调整。依据：色觉差异 |
| 品牌色相适配 | 锚点 | 不替换品牌色相，可调明度与彩度以适配层级与对比。依据：色彩恒常性、品牌调性 |

判定时点名的感知机制（14 条）：感知均匀空间（OKLCH / CIELAB）、对比度（WCAG 相对亮度比与 APCA Lc）、极性（负极性更易光晕）、空间频率与对比敏感度、透明度与合成、暗适应与浦肯野效应、光晕与眩光、同时对比与侧抑制、彩度与明度耦合（Helmholtz–Kohlrausch、Bezold–Brücke）、面积与彩度、色彩恒常性与环境、可区分色相有限、色觉差异、混合与渐变（在感知空间插值，避免 sRGB 插值的灰死与色带）。

## 文字与承载面的配对（专项，优先于全局判定）

1. **先定角色，再定对比**：承载阅读（正文段落、长句、表格内容）／辅助文字（标签、说明、时间戳、次级信息）／弱化文字（占位符、禁用态、装饰）／反色文字（按钮与色块上的前景）。弱化文字不得被复用到需要阅读的位置；反色文字必须针对实际填充色单独验，不能沿用页面结论。
2. **判定面取最差**：同一文字色会落在 bg / surface / elevated / card / hover / selection / accent 填充上，逐一测量，以最差的一个面作为该文字色的结论，不以 base bg 通过即算过。
3. **彩度与文字**：中性或低彩度色最适合承载正文（色差小，也不与状态色抢语义）；高彩度文字只用于短词、标题或点睛，小字号下须额外检查彩色边缘与色差。
4. **无障碍冗余**：正文对比不足时优先补对比，而不是换字体；若因品牌色必须低对比，须以字号、字重或背景色块补偿，不得只靠颜色承担区分。
5. **报告与判定分离**：报告沿用 WCAG 相对亮度比（便于跨主题复算与比较），判定用 APCA Lc（按官方字号—字重矩阵查表）并叠加感知机制。带 alpha 的结果记作「值 @ 面」，例如 4.8 @ card。

## 执行步骤

1. **阅读目标声明**：三到五句写明用途、阅读时长、信息密度、环境亮度、字号字重；后续所有尺度由此推出。
2. **角色还原**：依据明度与彩度分布，把原始色值映射到语义角色（底层背景 / 抬升面 / 浮层 / 边框分隔 / 正文 / 次级文字 / 弱化文字 / 点睛强调 / 品牌色 / 语义色 成功·警告·错误·信息），无法映射的单列。
3. **意图解读**：一句话说明配色想表达的情绪与调性，指出由哪几个色值承担这一表达。
4. **合成层清理**：先展开所有 alpha token（透明度、可能落点、沿叠加链合成后的实色）；带 alpha 的文字 token 必须给出最差合成面，作为后续矩阵的判定依据。
5. **文字—背景矩阵**：对每个文字 token 逐一测量它在各承载面上的相对亮度比（记账）与 APCA Lc（判定，按官方矩阵查表），按最差面下结论并标注该面名称。
6. **逐项判定**：走「判定表」十项，每行读出等级 + 默认起点 + 依据机制；默认起点可依目标浮动，浮动给理由。
7. **优化**：给出改后色值，逐个说明改了什么、为什么、服务哪个目标；改动量最小化，能保留的原值不动；改完重跑硬底线项、合成层清理与文字—背景矩阵，确认无回归。
8. **交付**：出快档四件；用户要完整报告时走深档。

## 卡住时怎么办（触发条件 / 一线修复 / 仍失败兜底）

读到症状先查这张表，别硬推。第三列是「前两步都没解决」时的动作，不是可选项。

| 触发条件 | 一线修复 | 仍失败兜底 |
| --- | --- | --- |
| 色值不是十六进制，或位数不是 3/4/6/8（脚本 exit 2） | 就地转换：把 rgb()/hsl()/命名色按浏览器口径换算成十六进制，重跑该子命令 | 仍解析不了就把它记为【不可计算】单列，判定表里该行写「无法判定 + 缺什么」，不猜、不跳过 |
| token 名不在 14 个标准名内（脚本 exit 2） | 按常见别名归一（`background`→`bg`、`ok`→`success`、`bg-surface`→`surface`、`muted`→`textMuted` 等），重跑 | 仍无法归一，就按明度与彩度分布把它映射到最近的标准角色，并在结论里写明这是一次人工映射 |
| 要测的承载面是 hover / selection / 半透明叠加层（脚本只认 14 个标准 token 名，没有这两个面） | 先 `composite` 把该面合成成实色，再挑一个结构上最接近的标准面名承载这个值（如 `matrix --surface card=#1c2128`），在矩阵表里把该列标注为真实面名（hover @ card） | 合成链超过两层或该面依赖未定的交互态，就在矩阵里单列并标【未定面】，不当成已通过 |
| 文字 token 带 alpha 但用户没给最差承载面 | 追问一次：这个文字色会落在哪些面上 | 用户不回就按该文字色在界面结构里最可能落的最暗面取值，结论标【假设】并写清假设错会改哪一行 |
| 用户给的色值缺关键角色（只有 bg 与 text） | 只对已给的角色下结论，缺的角色写【缺】 | 不补齐、不虚构 token；交付的 token JSON 只含实际给到的键 |
| 场景信息不全（没说时长或字号） | 只问影响结论最多的那一项（通常字号或字重），一次不超过 3 问 | 仍缺就取该场景的默认档并标【假设】，在结论里点明「结论随字号变化」 |
| 色觉模拟出现塌陷（`cvd` 报某对低于 0.10） | 先加明度差（改 L，不动色相），重跑 `cvd` | 明度差已被挤压到会影响层级时，改为要求形态或文字冗余（图标、下划线、标签），并在结论里写「仅靠颜色不可区分」 |
| `contrast` / `matrix` 判定不达标（exit 1） | 按缺口提字号、加字重、拉开明度差或改承载面，一次只动一个变量 | 用户要求保留原值时，给出「保留 + 补偿」方案（具体字号字重或承载面取值），并标明这是带条件的通过 |
| `preview` 注入失败（模板缺变量、路径不可写） | 检查 token 名是否与模板的 14 个变量一一对应；输出路径换到可写目录 | 仍失败就不交预览页，改交「色值 + 判定表 + JSON」，并在结论里说明预览页缺失的原因 |
| `oklch --to-hex "L C h"` 的 L / C / h 写错位置或 C 大到无法收缩（脚本报错 exit 2） | 按 `--to-hex "0.7 0.2 40"` 的引号三数形式重写；超色域时脚本自己按 0.96 收缩色度并在行尾标注，读到标注即说明已处理，不必再降 C | 收缩后色相明显偏移（h 变化 > 10°）就回到 OKLCH 原值交付，注明该色超出 sRGB，只有宽色域设备能正确显示 |

## 工具（精确数字必须来自这里）

`scripts/shese.py` 零第三方依赖，Python ≥3.10；`python scripts/shese.py <子命令> --help` 看参数。

| 子命令 | 用途 |
| --- | --- |
| `oklch` | 十六进制 ↔ OKLCH |
| `contrast <text> <bg>` | 单个配对的 APCA Lc 与相对亮度比；给 `--size` + `--weight` 时按官方矩阵定起步档，不给则按 `--role body\|aux\|hint` 档（60 / 45 / 30） |
| `composite` | 带 alpha 的颜色沿叠加链在 sRGB 空间合成 |
| `matrix` | 文字 token × 承载面矩阵，直接标出最差面；要求逐 token 推：`--tokens` 的 text 条目写 `{"hex": "#...", "role": "body", "size": 16, "weight": 400}` 可让每个 token 用自己的角色或字号字重，写字符串则沿用全局 `--role` / `--size` / `--weight` |
| `cvd <colors...>` | 三类色觉模拟 + ΔE-OK 可辨性（默认阈值 0.10） |
| `preview --tokens name=HEX --out <file> [--mode dark\|light]` | 把 token 注入 `assets/scene-preview.html` 生成填色副本；模板外壳用品牌主题色（来源见 `references/theme-source.md`），被审的只有注入的 14 个 token；注入的 bg 与 `--mode` 极性不符时在 stderr 提醒，不改退出码 |
| `selftest` | 官方测试向量锚定自检（改脚本后必跑） |

退出码：0 = 成功（对比与色觉类子命令即全部达标）／1 = 判定不达标／2 = 输入或环境错误。token 名支持 `bg-surface`、`text-muted`、`ok`、`warn`、`danger` 等常见别名，输出一律归一到 14 个标准名。

起步档由脚本按 APCA 官方字号—字重矩阵查表得出，禁止自行插值或凭记忆给数；脚本给的是单点判据，交付里仍要连区间与取舍代价一起给。

## 输入

标准输入包（缺失项按最合理假设执行并标注【假设】）：

1. 家族 / 主题标识
2. 色值集合：十六进制列表或带语义命名的 token
3. 用途与明暗模式
4. 不可改动项
5. 透明度信息：哪些 token 使用 alpha、透明度值、预期落点与最差背景面

生成轨另加：风格意图或症状词、禁忌（一票否决）、可选参考锚点（用户给的一两套「类似这个感觉」的色值）。

用户报的是主题仓库编号（如「#002 的配色」）或主题名时，按 `references/theme-source.md` 先取该主题 `palette.md` 的全表作为输入，编号每次都现读 `INDEX.json` 复核。

仅当缺失会直接导致结论错误时，才提出不超过 3 个问题。所有颜色按最终合成后的实色计算，不按 token 原值；透明度信息缺失时按不透明处理并标注【假设】。

## 输出契约

**快档（默认）**

1. **结论**：是否可用、最大问题是什么，一句话。
2. **决策摘要**：阅读目标声明（含【假设】/【覆盖】/ 不可改动项）→ 配色意图解读 → 语义角色映射 → 合成层清单（token｜透明度｜可能落点｜合成后实色｜最差面）→ 文字—背景矩阵（标出最差格，带 alpha 记作「值 @ 面」）→ 改动表（角色｜原值｜新值｜理由｜服务的目标）→ 建议保留项。
3. **场景预览页**：把色值填进模板的副本，直接在浏览器打开即可看到这套色在真实界面里的样子。
4. **token JSON**：可直接写回主题文件；token 命名以输入端已有命名为准，不随意增减。

**深档（用户要完整报告时）**：在快档基础上补全十项判定的实测与理由、色觉模拟校验结果、不确定项；固定 12 节的报告规范见 `references/audit-report.md`。

- 用户没给现成色值、只给风格意图或症状词，或要求再出几个方向时 → 见 `references/generate.md`：症状词到意图卡的翻译、候选生成规则与意图保真判据

- 用户报主题仓库路径、编号或主题名，或要求预览页套上品牌外观时 → 见 `references/theme-source.md`：取色三步、只读纪律、token 名对齐与外壳色 pin 规则

## Non-Goals

- 不做数据可视化色阶（顺序 / 发散 / 分类）：判据与 UI token 不同，用户明确问到时只说明该边界，不代做。
- 不做插画、摄影、印刷配色。
- 不替用户改品牌色相。
