# 故障处置（troubleshooting）

SKILL.md「卡住时怎么办」先做四类分诊，只留最高频的五类症状（色值格式、token 名、最差承载面、矩阵不达标、预览注入失败）；本文件收其余七类，每行末列写明「仍失败后能不能交」。两者合起来覆盖全部已知症状，条目互不重复。

| 触发条件 | 一线修复 | 仍失败兜底 | 仍失败时能否交付 |
| --- | --- | --- | --- |
| 色值缺角色（只有 bg 与 text） | 只对已给角色下结论，缺的写【缺】 | 不补齐、不虚构 token；token JSON 只含实给到的键；预览页必须渲满 14 变量时用同族占位值并标【占位·未判定】 | 可降级：标【缺】与【占位·未判定】 |
| 没给时长或字号字重 | 只问影响结论最大的一项（通常字号或字重），一次 ≤3 问 | 仍缺就取该场景默认档并标【假设】，结论点明「随字号变化」 | 可降级：标【假设】并写明结论依赖哪一项 |
| 色觉模拟塌陷（`cvd` 报某对低于 0.10） | 先加明度差（改 L 不动色相）重跑 `cvd` | 明度差已挤压到影响层级就改用形态或文字冗余（图标、下划线、标签），写明「仅靠颜色不可区分」 | 可降级：标形态冗余与残余灰区 |
| 要求档高于该承载面物理上限（纯白/纯黑也达不到） | 先量上限：`contrast "#FFFFFF" "<面>" --size N --weight W`（正极性用 `#000000`）；能提字号或加字重就提，把要求档降到上限内 | 不能改字号就判「该面不可承载此档」，给出该面可达最高档与差额，交用户裁：换面 / 改字号 / 带条件通过（见 thresholds 1.4） | 可降级：换面或带条件通过，附差额 |
| 计算层跑不起来（`python` 缺失、版本 <3.10、`shese.py` 损坏或 selftest 不通过） | 先 `python --version` 确认 ≥3.10，重跑 `shese.py selftest` 验文件完整；装好或取回原文件后重跑 | 仍不行就停：告知缺计算层，不手算、不凭记忆补 APCA 数；只交机制与待测清单并标【未实测】 | 阻断：数字类结论不能交 |
| 需求超边界（色阶 / 插画印刷 / 整套设计系统） | 说明边界并给一条替代路径（如顺序色阶改感知等步长取色），不代做 | 用户坚持就要：可算部分照算（层级、对比、色觉），不可算部分标【超出范围】，不硬套界面 token 判据 | 可降级：可算部分照交，不可算标【超出范围】 |
| `--to-hex` 参数给少了（exit 2）或三数位置写错（不报错） | 按 `--to-hex "0.7 0.2 40"` 引号三数形式重写；位置写错时脚本照算不报错，拿返回 hex 与预期明度对账（L 0.2 / C 0.7 只差位置即 #2c0900 对 #ff692d） | 略超色域不报错：脚本按 ×0.98 缩到入色域并标 `[超出 sRGB，色度收缩至 …]`，色度收缩是成功路径；C 大到 200 步也缩不进（实测 L 0.7 / C 12 / h 40）才报 exit 2 | 阻断：修好重跑前不交付 |

## 交付闸（失败之后能不能带条件交出去）

| 闸 | 判据 | 动作 |
| --- | --- | --- |
| 阻断 | CHECKPOINT 3 的五条硬底线任一复测不过｜影响数字结论的输入或环境错（exit 2、计算层跑不起来）未修好却已下结论｜token JSON、预览页与决策摘要三处同 token 不同值｜脚本失效或无输出却记「通过」 | 停止交付，摆出「改了什么 / 还差多少 / 需用户定什么」 |
| 可降级 | 承载面物理上限无解、色觉需形态冗余、缺角色或缺字号字重、需求超边界、预览页生成失败（未知 token 或路径不可写，exit 2；只影响外观，不影响数字结论） | 可交，但每条标条件（换面 / 改字号 / 冗余 / 【假设】【缺】【超出范围】）与代价；预览页失败改交「色值 + 判定表 + JSON」并说明原因 |
| 不是失败 | exit 1 的判定不达标（锚点差距；命中硬底线归阻断）；用户坚持保留原值；用户偏好与判据冲突 | 照常交付并标「带条件通过」：缺口 + 区间 + 推荐点 + 代价，不写成报错 |

任一阻断项未销，其他行算得再全也不许交付；降级项没标条件等于阻断。

## 静默失败复核（交付前六查，任一不过就回去补）

1. 每条命令里的 hex 都带引号——PowerShell 下裸 `#` 会吞掉该参数：有时报 exit 2，有时参数少一个却照样 exit 0（如 `delta` 给了三个、第三个被吞，只剩两个也判「通过」），两种都算没跑完；`delta` 的打出行数应等于传入颜色数 − 1，对不上就是被吞了。
2. 每个「通过」都能指到一条 exit 0 的脚本输出，不靠记忆、不手抄矩阵格点。
3. token JSON、预览页、决策摘要三处同一 token 同值。
4. 预览页是本轮新渲的副本（不是上一轮遗留的旧文件），`--mode` 标签与注入值的极性一致——极性不符时脚本只在 stderr 提醒、exit 仍是 0，不看警告就等于带病通过，stderr 告警要一并留档进交付。
5. 人工判断项在交付里标「人工判断」，不混进实测结论。
6. 结论里的数字与脚本输出逐字一致，不四舍五入、不补位、不用插值补查表结果。

## 退出码速查

| 码 | 处置 |
| --- | --- |
| 0 成功（判定类即全部达标） | 继续下一步 |
| 1 判定不达标 | 不是错误：按缺口提字号、加字重、拉明度差或换面，一次只动一个变量；结论附差额与代价 |
| 2 输入或环境错误（色值、token 名、参数、路径） | 先修输入再重跑；不要用改判定链的方式绕过 |

## 处置底线（任何一条都不得跳过）

- 不猜、不跳、不静默删除无法计算的项：算不了就单列写「无法判定 + 缺什么」。
- 不因脚本 exit 1 就改判定口径：exit 1 是结论不是故障。
- 静默失败按六查销项：没跑、没对账、没复核的项不许写进「通过」。
- 兜底方案必须保留原结论的适用条件（重跑步骤 4、5、6 确认无回归）。
- 交付里注明哪些行是人工判断而非脚本实测。
