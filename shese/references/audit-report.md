# 深档完整报告规范

本文件只规定深档报告的节次、字段与取数来源。执行顺序、判定链与三级标注的定义以 SKILL.md 为准，此处不复述，避免两份文件各说一套。

十三节顺序固定，不得增删或调换节次。脚本侧可用的子命令固定八个：oklch、contrast、composite、matrix、cvd、delta、mix、preview；下文「数据从哪来」只从这八个里点名。

## 1 结论

- 目的：让不读后面十一节的人也能拿到唯一需要的判断，且该判断可被继续追问依据。
- 必含字段：可用性（可用／有条件可用／不可用）；最大问题一句话；该问题所属等级（硬底线／参考锚点／目标推导）。
- 数据从哪来：可用性与不通过清单取 contrast 的 verdict 与 matrix 的 failed；「最大问题」必须由我按机制排序后选出一个，不能直接取脚本输出的第一条 FAIL——脚本按 token 顺序输出，并不知道哪个面承载的是长句正文。
- 何时可省：不可省。

## 2 阅读目标声明

- 目的：把后续所有尺度的来源写在开头，使后面出现的每个数字都能反查到具体目标。
- 必含字段：用途；单次阅读时长；环境亮度；信息密度；字号与字重（逐个文字 token 给）；输入缺失项用【假设】标注；用户显式覆盖的项用【覆盖】标注；不可改动项（品牌色相、既有 token 命名、用户点名保留的色值）。
- 数据从哪来：无脚本来源，直接取输入端。字号与字重是后文 contrast 的 --size／--weight 与 matrix 同名参数的实参来源，必须在此处先定，不得在测量时临时改。
- 何时可省：不可省（目标先行是 SKILL.md 的不可违背项）。

## 3 配色意图解读

- 目的：先记录这套色本来的表达，避免优化阶段把承担情绪的色值当成缺陷改掉。
- 必含字段：一句话情绪与调性；由哪几个色值承担（点名 token 与 hex）；哪几个色值承担「安静」、哪几个承担「点睛」。
- 数据从哪来：oklch 给出每个色值的 L／C／h：用明度次序说明层级，用彩度大小说明情绪音量，用色相说明分类与温度。情绪本身的命名与归因由我判断，脚本不做这一步。
- 何时可省：用户明确只要可读性结论且不要调性说明时可省，省略须在报告中写明「本节按用户要求省略」。

## 4 语义角色映射

- 目的：把一串色值变成有职责的角色，后续判定才有「这个 token 承载什么」的前提。
- 必含字段：每个色值对应的角色；无法映射的色值单列；映射依据（该色值的明度与彩度在整组里的位置）。
- 数据从哪来：oklch 的 L／C 分布给出量化次序；token 名的合法性由 matrix 与 preview 共用的白名单校验（非法名会在子命令里直接报错）；角色的最终归属与「无法映射」的判断由我做。
- 何时可省：不可省。
- 说明：角色名沿用输入端已有的 token 命名，不新增 name。

## 5 合成层清单

- 目的：把「带 alpha 的颜色没有固定观感」落到一张可复查的账上：判定对象只能是合成后的实色。
- 必含字段：五列表格，列为 token｜透明度｜可能落点｜合成后实色｜最差面；多重叠加沿整条链展开（半透明文字落在半透明背景或 hover 叠加层上），不是只算一层。
- 数据从哪来：合成后实色取 composite，逐个落点跑一次 --on BASE LAYER...；模板自带的混色底（color-mix）先用 mix 按同一比例在 oklab 复算成实色，或按浏览器口径 composite 还原，不能因为「模板给的」就跳过；「可能落点」清单由我从界面结构推断——脚本不知道某个 token 会出现在哪些面上，这一步不能交给脚本。
- 何时可省：无 alpha token 时不得删节，保留表头并写明「无 alpha token」，否则读者无法判断是漏算还是确实不存在。

## 6 文字—背景矩阵

- 目的：给出每个文字 token 在其全部承载面上的实测并锁定最差格，避免用 base bg 一格的结论覆盖全站。
- 必含字段：五列表格，列为 文字 token｜承载面｜WCAG 相对亮度比｜角色｜建议与依据机制；最差格须显式标出；带 alpha 的格子记作「值 @ 面」，值取该面上的合成实色。
- 数据从哪来：整张表、最差格与 failed 清单取 matrix；WCAG 一列取 cells[].wcag_ratio，合成实色取 cells[].composited。脚本只给通过／不通过，因此「角色」列与「建议与依据机制」列必须由我补：角色按该 token 的实际阅读职责定，建议要写清依据的是哪条感知机制。
- 要求逐 token 推：把 tokens.json 里 text 条目写成对象（{"hex": "#...", "role": "aux", "size": 14, "weight": 400}），matrix 会为该 token 单独推要求（给了 size + weight 走官方矩阵，否则走该角色的锚点档），并在 texts[] 里给出每个 token 的 required_lc 与 tier；正文与次级／弱化文字绝不共用同一个要求值。CLI 的 `--text name=HEX` 只能用全局 `--role` / `--size` / `--weight`。
- 何时可省：不可省。
- 口径：本节是报告口径，只记 WCAG 相对亮度比；判定口径见第 7 节与文末「报告与判定的分离」。

## 7 判定与建议表

- 目的：把矩阵的实测翻译成各审查项上的可执行建议，并标明每条依据的是哪条机制。
- 必含字段：四列表格，列为 审查项｜等级｜实测｜建议与理由（含依据机制）；审查项逐项覆盖 SKILL.md 判定表的十二项；等级按三级标注；建议给区间加推荐点与取舍代价，不以通过／不通过收尾。
- 数据从哪来：能直接算的取脚本——承载阅读的正文对比取 contrast 或 matrix，文字 token 含 alpha 取 composite 与 matrix，色觉模拟校验取 cvd，控件边界与纯分界取 contrast 的非文本档与 delta；其余八项（次级／弱化文字、层级明度差、高彩度色的面积、大面积填充彩度、深浅模式基础色、语义色可区分性、品牌色相适配、要点与品牌强调）脚本给不出，必须由我结合 oklch 的 L／C 分布与界面结构判断。
- APCA 要求值的写法：可直接写出的官方矩阵锚点只有三个——16px／400 对应 Lc 90，24px／400 对应 Lc 60，32px／400 对应 Lc 50。其余任何 APCA 要求值一律写成「按官方字号-字重矩阵查表（scripts/shese.py 的 apca_required_lc）」，不得写死具体数字；实测值取 contrast 或 matrix 输出里的 apca_lc。
- 何时可省：不可省。

## 8 优化后色值表

- 目的：给出可直接替换的最小改动集，并让每处改动能回溯到它服务的目标。
- 必含字段：五列表格，列为 角色｜原值｜新值｜理由｜服务的目标；改动量最小，能保留的原值不动；新增色值必须对应一个已存在的语义缺口，不为「更高级」引入新色相。
- 数据从哪来：新值在感知空间里调 L／C 后用 oklch --to-hex 转回 hex，不直接在 hex 分量上加减；派生档（hover、淡底、叠层）用 mix 在 oklab 生成，禁用 color-mix(in srgb) 的结果；改完必须重跑 composite、matrix 与 contrast 的硬底线项确认无回归，并把重跑结果写进本节或第 12 节。
- 何时可省：无问题时写「无需改动」并给出保留依据，不删节。
- 边界：品牌色相不改；若品牌色造成可读性问题，只在理由列指出并给替代用途。

## 9 建议保留项

- 目的：明确写下「这些看着可疑但我判定要留」的色值，防止下一轮评审或后续会话把它们当成问题改掉。
- 必含字段：保留的 token 与原值；保留理由；它承担的表达或职责。
- 数据从哪来：oklch 的 C 与 h（高彩度点睛、品牌色相）；第 7 节中已通过的审查项。
- 何时可省：不可省；确无保留项时明写「无」。

## 10 色觉模拟校验结果

- 目的：验证语义色不只靠色相区分，排除只对正常色觉成立的配色。
- 必含字段：三类模拟（protan／deutan／tritan）下每个语义色的模拟值；会被并列使用的语义色两两之间的可辨性结果；判定为必须两两可辨的色对清单；不通过的对与其补救方向（补明度差，或加形态／文字冗余编码）。
- 数据从哪来：模拟值与两两可辨性取 cvd（脚本按其自记录的最坏情况口径跑，--min-delta 的默认值见子命令帮助）；「哪些色对必须两两可辨」由我按语义角色是否会被并列使用判断，脚本不知道使用关系。正文在模拟后是否仍可读，要把模拟得到的 hex 再喂给 contrast 复测一次，不能只看 cvd 的可辨性结论。
- 何时可省：配色不含语义色也不含状态区分时，写「不适用」并给出不适用理由；这是硬底线项，省略必须交代理由。

## 11 token JSON

- 目的：给出一份可直接写回主题文件的完整骨架，键位齐全，写回前只需替换实测值。
- 必含字段：family、theme、mode、tokens、alphaTokens、contrast、changed、unchanged、notes。tokens 的十四键与脚本白名单一致；alphaTokens 逐 token 记 alpha、base 与 composited；contrast 固定四键（text/bg、text/surface、textMuted/bg、textDim/bg）；changed 与 unchanged 记 token 名；notes 记口径与遗留假设。
- 数据从哪来：tokens 取第 8 节的新值（未改动项取原值）；alphaTokens 的 composited 取 composite；contrast 四个键取 matrix 对应格子的 wcag_ratio，属记账口径，判定结论不进 JSON。
- 何时可省：不可省。
- 骨架（null 与 #rrggbb 是待填占位，写回主题文件前必须替换为实测值）：

## 12 不确定项

- 目的：把没验证的部分与假设逐条交出来，让报告可被复算或被推翻。
- 必含字段：每条包含 缺什么输入｜采用了什么假设｜该假设若错会改变哪一条结论｜复算需要什么。
- 数据从哪来：无脚本来源，由我在全流程记录。透明度信息缺失时按不透明处理并标注【假设】，该假设必须在此处重列一次，因为它直接影响第 5、6、7 节。
- 何时可省：不可省；没有不确定项时明写「无」。

## 13 人眼验收与机检自检

- 目的：把「脚本全绿」与「人看着舒服」分开交付，避免用机检通过掩盖指标定不了的问题。
- 机检自检（交付前逐条打勾，缺一条即报告不完整）：
  1. 分角色判定：每条结论都绑定了角色（承载阅读／次级／点睛等），没有「一套色一个总评」。
  2. 多表面：每个文字 token 在全部承载面上都测过，而不是只测 base bg。
  3. 相邻档：层级相邻档之间的 ΔE-OK 实测过，没有靠单点对比值代替。
  4. 混色空间：全量搜过 color-mix(in srgb)，命中即记缺陷并按 oklab 复算。
  5. 彩度上限：大面积填充的 OKLCH C 记了实测值，不是只说「降一点」。
  6. 一 token 多职：兼两职的 token 两职都验过。
  7. 恒定性：不随主题变化的层（品牌色、固定语义色）没有被主题变量重写。
  8. 未定义变量：引用了但没定义的 token 单列出来，不算通过。
  9. 脚本失效报警：任一子命令非零退出或输出异常时必须在报告里写明，不得静默当作 PASS。
- 人眼验收（三张产物，缺一张就要在报告里写明未做）：
  1. 同页深浅两主题并排截图；2. 正文 100% 缩放样张；3. 主按钮与淡底标签特写。
- 指标看不见、必须人眼看四类：品牌分量是否还在、层级存在感是否够、冷暖是否统一、图标与语义色是否一致。任一项判断没有脚本来源，必须在第 13 节写明「已人眼查看」或「未人眼验收」。
- 何时可省：不可省；人眼验收确实无法进行时，写「未人眼验收」并列出因此未覆盖的判断。

## 报告与判定的分离

- 报告口径用 WCAG 相对亮度比记账：它可跨主题复算与横向比较，落在第 6 节的表格与第 11 节的 contrast 字段里。
- 判定口径叠加 APCA 与感知机制：APCA 随字号与字重变化，机制覆盖对比度、极性、空间频率与对比敏感度、光晕与眩光、面积与彩度、色觉差异等。判定结论不写回报告的对比数字栏。
- 两者不可混用：不得用 WCAG 相对亮度比直接下结论，也不得只留 APCA 值而丢掉可复算的记账值。
- 每个带 alpha 的结果必须带「值 @ 面」，值取该面上的合成实色；未声明基准面的对比数字一律视为无效，不进报告。
