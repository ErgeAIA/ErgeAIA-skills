# 场景画像与尺度推导（scenes）

本文件只在把阅读目标落成尺度时读。判定表的十二项、三级标注与专项口径见 SKILL.md；机制为什么这样起作用见 references/mechanisms.md。本文件不重复判定表全文，只给出「目标 → 尺度」的推导路径；出现的具体数字刻度以 references/thresholds.md 为唯一真相源。

## 为什么不能拿通用数字套场景

SKILL.md 不可违背第 1 条要求目标先行：先声明阅读目标（用途、单次阅读时长、环境亮度、字号与字重、信息密度），再由目标反推尺度。原因有三层：

- 通用数字是某一场景下的默认刻度，不是门禁。同一条起步档，在长读场景是下限，在扫读场景可能已经过高，在密集小字场景又不够。SKILL.md 不可违背第 2 条把机制与数字分开，数字只作默认刻度。
- 尺度之间互相耦合，单独套一个数字会压坏另一头。字号档位一升，负极性下的光晕上限也要下压；彩度一提，感知亮度也跟着变（见 references/mechanisms.md 的耦合节）。逐个数字照抄，等于把这些耦合关系当成不存在。
- 「合格」不是一个二值结论。同一个字号，长读场景要的是舒适区间，扫读场景要的是短时扫得动的可用性；目标不同，结论必然不同（SKILL.md 不可违背第 4 条）。

正确顺序：声明目标 → 定位场景画像 → 由画像给出尺度推导方向 → 用官方字号-字重矩阵查表把方向落成起步档 → 逐项判定 → 按目标给区间与推荐点。场景画像不是标准答案表，而是把目标翻译成尺度方向的中间层；用户声明的目标与画像不一致时以用户声明为准，并在报告里写明覆盖。

## 代码编辑器

**用途**：长时间集中阅读与编辑代码，字符级辨认（括号、变量名、标点）多于句子级阅读；同一屏内混合语法高亮、字符串、注释与错误标记。

**单次阅读时长**：长时段、连续、中断频率低。（用户未声明时的【假设】；实际以声明为准。）

**环境亮度**：室内中低亮度居多，夜间与白天差异大，屏幕常常是主要光源。

**典型字号与字重**：正文小字号、常规字重，注释与状态栏更小或更弱。本画像不写死 px：以用户声明的 size 与 weight 为准，未声明时按【假设】取值并在报告里显式写出。锚点校准：16px/400 → Lc 90、24px/400 → Lc 60、32px/400 → Lc 50 是官方矩阵上的三个点，用来判断假设值落在哪一档。

**信息密度**：高。多列、多行、密集 token，注意力停在局部字符而不是整段。

**由目标推出的尺度**：
- 正文对比起步档：由「长时间连续读 + 小字号 + 高密度」目标推出 → 查官方字号-字重矩阵得到起步档（以实际 size 与 weight 按 scripts/shese.py 的 apca_required_lc 查表）。这是四条画像里最严的一档，因为空间频率最高、持续时长最长。
- 辅助与弱化文字的相对位置：由「注释、行号、状态栏不承载长句、只承载短标签」目标推出 → 可低于正文起步档，但只允许落在短标签位置；行号这类极短文本可以更弱，注释属于可能被读成句子的对象，不得降到弱化档。
- 层级明度差：由「同屏多层级要在扫视中立刻分开」目标推出 → 相邻层级在 OKLCH 的 L 上拉开可辨差距（见 SKILL.md 判定表第 4 项）；深色模式的间隔通常要比浅色更大。
- 彩度与面积预算：由「彩度会与语法高亮争夺注意力」目标推出 → 背景、卡片、编辑区保持低彩度；彩度留给语法高亮与语义标记，且限制在小面积、短 token 上。
- 极性取用倾向：由「环境亮度偏低 + 长时间阅读」目标推出 → 倾向负极性（深底浅字），但必须按 references/mechanisms.md 第 7 条压住光晕上限，不用纯黑底与纯白正文。

**该场景最容易犯的错**：把「代码看起来清楚」等同于「对比够高」，深色下把正文推到纯白；把注释提到与正文同档，反而让层级消失；用高彩度背景块标注错误行，让它在扫视中与语法高亮抢注意力；只判一套色，不按用户实际字号重判。

## 网页长文

**用途**：以段落为单位的连续阅读，含标题层级、引用、列表、链接与脚注；读者的目标是把内容读完。

**单次阅读时长**：长时段连续阅读，段落之间没有强制停顿。

**环境亮度**：不确定，日间与夜间都可能；页面自身底色就是主要阅读面。

**典型字号与字重**：正文中等字号、常规字重；标题更大字号或更粗字重。px 以用户声明为准，未声明时标【假设】并写出；可用三个官方锚点判断落在哪一档（16px/400 → Lc 90、24px/400 → Lc 60、32px/400 → Lc 50）。

**信息密度**：中低。单列为主，行宽长，眼睛在行内持续移动。

**由目标推出的尺度**：
- 正文对比起步档：由「长句连续阅读 + 中等字号」目标推出 → 查官方字号-字重矩阵得到起步档（scripts/shese.py 的 apca_required_lc）。与代码编辑器相比可以略低于字符级辨认的档位，但仍按长读口径取。
- 辅助与弱化文字的相对位置：由「脚注、图注、日期是短标签或低频长句」目标推出 → 标签型可低于正文；图注、脚注只要不短，就按正文起步档处理，不因为「它是辅助信息」而降低。
- 层级明度差：由「标题—正文—引用三层在一个视口内即可辨认」目标推出 → 相邻层级在 OKLCH 的 L 上拉开可辨差距；正文与底色的差靠对比档承担，不要用层级差去补对比。
- 彩度与面积预算：由「大面积阅读底色不与正文争夺注意力」目标推出 → 底色低彩度；链接与强调色用小面积，且它的对比要按实际落到的面单独判（hover 面单独算）。
- 极性取用倾向：由「日间与夜间都可能读」目标推出 → 深浅两版都要出，倾向由环境亮度决定；不用一套结论覆盖两版（SKILL.md 不可违背第 12 条）。

**该场景最容易犯的错**：把链接色当强调色调高彩度，行内文字被切碎；只判 base bg 上的正文，忽略引用块、卡片与脚注面；深色版直接由浅色版反相；行宽过长导致跳行，却把问题归给对比度。

## 移动端卡片流

**用途**：快速扫读一串卡片，单条信息量小，目标常常是「扫到想看的那张再决定停不停」。

**单次阅读时长**：短时段、中断频率高，单张卡片内的阅读极短。

**环境亮度**：变化最大（户外强光到夜间床上），环境光经常压过屏幕亮度。

**典型字号与字重**：小字号为主，标题略大或加粗；字号受物理屏幕尺寸限制，以用户声明为准并标【假设】。

**信息密度**：中高，但注意力是跳跃的（卡片之间不连续）。

**由目标推出的尺度**：
- 正文对比起步档：由「短时扫读 + 小字号 + 环境光干扰」目标推出 → 查官方字号-字重矩阵得到起步档（scripts/shese.py 的 apca_required_lc）。单次阅读短，可比长读场景宽松；但环境光会吃掉一部分余量，所以不能一路紧贴地板。
- 辅助与弱化文字的相对位置：由「时间戳、来源、标签是短标签」目标推出 → 可明显低于正文；但它们参与同一次扫视，不能低到与正文混成一片，跳读需要边界。
- 层级明度差：由「卡片内标题—正文—元信息三层要在一次扫视内分开」目标推出 → 相邻层级在 OKLCH 的 L 上拉开可辨差距；卡片之间与卡片之内分别算，避免层级互相淹没。
- 彩度与面积预算：由「卡片面积大、数量多、常在强环境光下看」目标推出 → 卡片底与大面积区域低彩度；强调色（未读点、标签）小面积，并且必须有形态或位置上的冗余。
- 极性取用倾向：由「环境亮度多变」目标推出 → 跟随系统或跟随环境，两版都要给；强光下亮底往往更稳。

**该场景最容易犯的错**：把「扫读」理解成「可以低对比」，把元信息压到几乎看不见；用大面积高彩度卡片底做分类；让颜色单独承担未读／已读这类状态；只出一版（默认浅色）就交付移动端。

## 通用兜底

**用途**：用户没说清场景，或场景混杂（一次给多个界面、评审一个主题文件）时使用。

**单次阅读时长**：未知。（【假设】：按长读与扫读都不得出错的保守口径。）

**环境亮度**：未知。（【假设】：按日间与夜间都要可用的双模式口径。）

**典型字号与字重**：未知，取中等字号加常规字重。（【假设】；用户声明后必须覆盖，不得沿用。）

**信息密度**：未知，按中等密度处理。

**由目标推出的尺度**：
- 正文对比起步档：由「场景未知 + 长读与扫读都不能出错」目标推出 → 查官方字号-字重矩阵得到起步档（scripts/shese.py 的 apca_required_lc），取长读一侧而不是扫读一侧，因为未知场景里的最坏情况通常是长读。
- 辅助与弱化文字的相对位置：由「辅助信息实际会不会被读成句子未知」目标推出 → 只允许低于正文用于短标签；任何可能被读成句子的文字按正文档处理。
- 层级明度差：由「同屏层级数未知」目标推出 → 相邻层级在 OKLCH 的 L 上拉开可辨差距，深浅两版分别给。
- 彩度与面积预算：由「面积分布未知」目标推出 → 按最坏情况（大面积、常驻）收紧彩度，点睛小面积可放宽。
- 极性取用倾向：由「环境与偏好未知」目标推出 → 深浅两版都给出一段可用区间，并说明这段区间随哪一项目标收窄。

**该场景最容易犯的错**：把兜底档当标准答案直接交付，不追问；不标【假设】就让用户以为这是针对他的场景给的结论；给的区间过窄，用户换个字号就失效；把兜底结论用到数据可视化色阶上（越界，见 SKILL.md Non-Goals）。

## 同一个字号换场景怎么变

同一套色值，改动的是「哪一项尺度」要能指出来，否则用户无法复算。以 12px 与 20px、长读与扫读两组变量为例：

- 12px 与 20px 的不同结论：变的是正文对比起步档这一项。字号是空间频率的输入，12px 落在高空间频率一侧，起步档更高，可能不通过；20px 落在低空间频率一侧，起步档更低，同一套色值可能就通过。两个字号下要改的都是起步档这一个量，而不是换一套颜色；处理顺序是先提字号或加字重，再决定是否动色值（SKILL.md 不可违背第 9 条）。查法：把实际 size 与 weight 代入 scripts/shese.py 的 apca_required_lc；16px/400 → Lc 90、24px/400 → Lc 60、32px/400 → Lc 50 可用来判断这两个字号各自靠近哪一档。
- 长读与扫读的不同结论：变的是三个量——正文对比起步档（长读更严）、辅助与弱化文字的相对位置（扫读下元信息仍要可辨边界，不能一路放松）、彩度与面积预算（长读下大面积彩度要更保守，因为它持续参与）。字号不变而场景变时，先动的是对比起步档与面积预算，最后才考虑色相。
- 两者叠加：小字号加长读是最严组合（起步档最高），大字号加扫读是最宽组合（起步档最低）。这里的「最严／最宽」只指起步档方向，不指某个固定数值；具体档位按官方字号-字重矩阵查表（scripts/shese.py 的 apca_required_lc）。

改场景时必须在报告里写明改的是哪一项尺度、为什么、代价是什么（SKILL.md 不可违背第 5 条）；只说「这个场景下不合适」而不指出动的是哪一项，用户既无法复算也无法反驳。
