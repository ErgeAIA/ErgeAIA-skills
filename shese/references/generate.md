# 生成轨：从一句意图到 2–3 套候选

何时读：用户没有给现成色值，只给了风格意图、症状词、参考锚点或主题编号时；或用户给了一套色但要求「再出几个别的方向」。

生成轨不另立判据：候选生成完之后，**必须逐套走同一条判定链**（SKILL.md 执行步骤 1–8），不得跳过判定直接交付。

## 一、三个入口

| 入口 | 用户话术 | 你要做的 |
| --- | --- | --- |
| 症状词入口 | 「太吵」「发灰」「刺眼」「闷」「廉价」「高级但别性冷淡」 | 把症状词翻译成可判定的意图卡（见第二节） |
| 参考锚点入口 | 「像这几张图」「照这个品牌色来」 | 从锚点里提取色相家族与明度骨架，**不照抄色值、不改写源色值** |
| 权威源入口 | 用户报主题编号或主题名（如 #048 kanagawa/wave） | 按用户点名去读该色板原文，以其色值为候选基础；源色值只引用不改写 |

缺场景信息时按最基本场景（通用长文）执行并标【假设】，不要因为想要「更准」而先问一堆。

## 二、症状词 → 意图卡

意图卡固定六栏，写完先给用户看一眼再出候选（一句话即可，不要展开成长文）：

1. **调性**：安静 / 克制 / 活泼 / 严肃 / 暖旧 / 科技……（一到两个词，不许列五个）
2. **色相家族**：主色相落在哪一段（如冷蓝—青、暖橙—红），以及允许的次要色相
3. **明度骨架**：底色档位、层级跨度、正文相对底的方向（正/负极性）
4. **彩度预算**：大面积填充走低彩度还是中彩度、点睛色允许到高档
5. **对比策略**：靠什么建立层级（明度差为主、色相为辅、还是靠面积与留白）
6. **禁忌**：用户给的一票否决项，原文照记

症状词翻译示例（按此粒度，不要更细）：「太吵」→ 高彩度面积过大或色相数过多；「发灰」→ 彩度整体塌到近中性、层级明度差不足；「刺眼」→ 极性与对比双向过冲（纯白/纯黑端点、亮底亮字）；「闷」→ 明度骨架跨度过小、大面积与点睛都是同一档明度。

## 三、候选生成规则

- 出 **2–3 套**，且必须**结构不同**：明度骨架不同、或彩度分布不同、或色相家族策略不同。**只换色相不算不同结构**。
- 每套用一句话说明它服务哪个目标、代价是什么（例如「明度跨度更大换来更清晰的层级，代价是暗部细节更少」）。
- 每套都要能被同一个意图卡解释：不能让用户觉得「有两套不是我要的」。
- 候选落地时同步给出语义 token 映射，命名以用户输入端已有命名为准；用户没有命名时用 SKILL.md 的 14 个 token 名。

## 四、禁忌处理

禁忌是**一票否决**，不是扣分项：候选里命中禁忌即整条弃用并说明命中在哪。不得交付「大部分满足但有少量禁忌色」的候选。

## 五、意图保真判据（改色时必须同时满足）

生成轨与审查轨的优化阶段共用这条判据，用来防止「越改越像另一套配色」：

1. **色相家族不变**：主色相所在色相段不迁移。
2. **基本色相数不增**：承担分类与情绪的色相数量不增加（可快速命名的基本色相数量有限）。
3. **彩度关系不反**：原本低彩度大面积不能改成高彩度大面积；原本的点睛色不能变成底色。
4. **点睛面积不扩**：最高彩度只允许出现在不大于原来的面积上。

四条任一被击穿，就要么退回改动、要么明确告诉用户「这已经是一套新配色，不是优化」。

## 六、生成后必须做的两件事

1. **逐套过判定链**：含阅读目标声明、层级明度差、面积—彩度、色觉可辨（三类模拟）。任一套被硬底线拦下就改或弃。
2. **出预览页**：用 `scripts/shese.py preview` 把候选填进 `assets/scene-preview.html`，让用户直接看见；多套候选各出一份，命名带候选序号。

## 七、不做

- 不为「更高级」引入新色相（新增色值必须对应已存在的语义缺口）。
- 不替用户改品牌色相；品牌色造成可读性问题时只指出并给替代用途。
- 不建色卡库、不联网找配色、不做数据可视化色阶（顺序 / 发散 / 分类）。
