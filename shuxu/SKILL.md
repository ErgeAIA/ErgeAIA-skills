# 书序 · Shuxu

> 书序者，冠于卷首，序其意旨。项目之要，一序而明。

## 定位

**书序（shuxu）**：为代码项目撰写 / 优化 README 的技能。分析仓库 → 生成新 README 或增量优化已有 README，读者是**外部开发者**——第一次接触项目的人，他们想 3 秒判断价值、5 分钟跑起来、10 分钟接入或贡献。

最高准则：**真实性优先，禁止幻觉**——只写从代码确认的事实，未验证内容显式标注，命令与清单文件字面一致。

**方法论**（做法优于答案）：先给可直接执行的步骤，再讲原理；示例先于解释，来源先于结论——读者要的是「照着做就能得到结果」，不是理论正确。

## 边界与路由

| 意图 | 处理 |
|---|---|
| 生成 / 优化项目 README | ✅ 本 skill 主场 |
| 公众号长文 / 技术博客 | → zhubi / long-article |
| 完整 API 文档套件（多文件 docs/） | ⚠️ 超范围（README 只做导航，深度链到 docs/） |
| 非 Markdown 文档 | ❌ 不做 |

## Non-Goals

- ❌ 不编造功能 / 徽章 / 截图 / 链接 / star 数 / 版本号（每条宣称可追溯）
- ❌ 不写公众号长文 / 技术博客（交 zhubi / long-article）
- ❌ 不构建完整 docs/ 文档体系（README 只做导航）
- ❌ 不执行有副作用命令（发布、写库、发请求、修改代码）
- ❌ 优化场景不强套模板（尊重原文档风格，只做必要增删改）

## 快速管线

```
① 模式确认 → ② 只读分析 → ③ 写作（生成模式） 或 ④ 优化（增量模式） → ⑤ 验证 → ⑥ 收尾自检
```

> **③ 与 ④ 是互斥分支，不是串行两步**：生成模式走 Step 3 后跳到 Step 5；优化模式跳过 Step 3，走 Step 4 后进 Step 5。正文编号与管线一致（六段）。

### Step 1：模式确认

- **输入契约**：仓库路径（本地目录或 Git 地址）缺失 → 显式输出 [待澄清] 询问，不静默开始；路径不存在 / git 拉取失败 / 目录不可读 → 中止并说明原因，不降级继续。
- **可见性**：开源（有 LICENSE / 公开 remote / .github）或私有（用户指定）——无法判断时问用户。
- **语言**：**默认中文主文件**（README.md 中文）；开源项目按需补英文版 README.en.md（双语平行互链）；私有项目单文件中文。
- 用户显式指定的模式 / 语言优先于默认。

🔴 **CHECKPOINT**：可见性或语言无法从仓库证据判断时，先输出 [待澄清] 询问，确认后再进入 Step 2——不猜测默认值。

### Step 2：只读分析（此阶段不写任何内容）

1. **清单文件**：package.json / pyproject.toml / Cargo.toml / go.mod / requirements.txt 等——名称、版本、scripts、依赖、入口、构建系统、**engines 版本要求**。
2. **入口与核心 API**：主入口、CLI 定义、配置项、环境变量、3-5 个最重要的公开命令 / 函数。
3. **测试与 CI**：测试命令、CI 工作流、目标平台矩阵。
4. **元信息**：LICENSE、CONTRIBUTING、CHANGELOG、docs/ 目录、旧 README。
5. **来源记录**：为每条将写入 README 的事实记录来源（文件名 + 键名/行号）。

**分析阶段失败分支**：
- 清单文件缺失（无 package.json / Cargo.toml / pyproject.toml 等）→ 基于现存文件（旧 README / 文档 / 源码入口）继续，并在收尾清单标注「来源局限：无清单文件」。
- 无 LICENSE / 无法判断可见性 → 回到 Step 1 的 🔴 CHECKPOINT 询问用户。
- 语言混杂或结构非常规 → 按主导语言 / 结构处理，并在收尾清单记录差异。

**产物**：来源记录表（每条事实 → 文件名 + 键名/行号）。

🔴 **CHECKPOINT（动笔前）**：向用户展示只读分析摘要（技术栈 / 核心功能 / 命令清单 + 来源）与将采用的模式 / 结构取舍，确认后再进入写作分支（Step 3 或 Step 4）。

**跳过条件（与家族「编排自动模式」同构）**：编排层以非交互方式调用，或用户明确要求「一步到位」时，跳过本暂停并直接进入对应分支；人工默认调用仍走强制确认。跳过时须在收尾清单标注「已跳过动笔前确认」。

### Step 3：写作规则（生成模式分支）

> **仅生成模式进入本步**；优化已有 README 请跳到 Step 4。二者互斥，不串行执行。

1. 只写代码中确认的事实；推断标 [推测]、无法确认标 [需核实]。
2. 安装 / 运行 / 测试命令必须与清单文件或项目内文档**字面一致**；不一致以代码为准，并在收尾清单记录差异。
3. 不编造：功能、徽章、截图、链接、star 数、版本号。徽章仅用真实来源（CI 状态 / License / 版本）。
4. 版本信息注明最低支持版本与已验证环境（**以清单文件 engines / requires 为准**，不凭记忆）。
5. 示例先于解释，附预期输出；配置项用表格呈现。
6. 结构遵循 `templates/` 模板，按项目复杂度裁剪，不机械照搬。
7. 双语：双文件章节平行并互链语言切换链接；术语全篇一致，首次出现可附中英对照；代码与命令保持英文。
8. 长度：快速可用项目单文件 150-300 行；复杂项目速览精简，深度内容链到 docs/，README 只做导航。

**产物**：README 草稿全文。完成后 → **Step 5**（跳过 Step 4）。

### Step 4：优化已有 README（增量模式分支）

> **仅优化模式进入本步**；从零生成请走 Step 3。与 Step 3 互斥。

1. 保留仍准确的历史信息（版本史 / 致谢 / 版权）。
2. 逐条核对现有声明：过时内容删除或改写，无法核对标 [待验证]。
3. 尊重原文档标题层级风格，不强套模板，只做必要增删改。
4. 输出末尾附改动摘要：新增 / 删除 / 修正 + 依据文件。

**产物**：改动摘要（新增 / 删除 / 修正 + 依据文件）。完成后 → **Step 5**（跳过 Step 3）。

### Step 5：验证

1. **命令验证**：只运行**无副作用命令**（`--help` / `--version` / 本地 build / test——build 会写本地产物、test 可能写缓存，均为本地环境内可回滚操作，不对外部世界造成影响）；**禁止命令清单**：publish、写库、发请求（**WebFetch 只读抽查 URL 除外**——见 5.2，只读 GET 不构成副作用）、改源码等。每条示例命令必须显式二选一标注 `[已运行验证]` / `[未经运行验证]`——无标注即禁止（防幻觉：未验证宣称滑向编造）。
2. **链接检查**：README 内所有链接与文件路径的连通性（相对路径指向真实文件；URL 可 WebFetch 抽查）。
3. **输出**：生成场景输出完整 README 全文；优化场景输出全文 + 改动说明。

### Step 6：收尾清单（必须逐项输出）

- 已确认事实及其来源
- 推断项
- 待用户确认项
- 明确不做项
- （若跳过动笔前确认）标注「已跳过动笔前确认」及原因

## 模板

- `templates/oss-bilingual.md`：开源双语（README.md 中文主文件 + README.en.md 英文平行版）
- `templates/private-zh.md`：私有项目单文件中文

## Gotchas

- **版本要求以清单文件为准**：Node / pnpm / Rust 版本必须核对 engines / packageManager / requires（教训：README 写 Node 18+ 但 Vite 7 实际要求 20.19+，见 ErgeMD 实战记录）。
- **动态徽章不可本地验证**：GitHub stars / downloads 等 shields.io 动态徽章数字无法离线确认，标注「动态值」；badge URL 连通性用 WebFetch 抽查。
- **发布构建 ≠ 开发构建**：多步发布链（版本同步、产物重命名）常封装在 script（如 `tauri:build`），README 若只写单命令需注明或指向封装命令。
- **双语互链**：README.md 与 README.en.md 必须互相放置语言切换链接，防止断链。
- **私有项目防污染**：私有模式严禁出现贡献指引、公开徽章等开源元素。

## Plan-Validate-Handoff 模式

Plan（Step 1 模式确认；Step 2 分析结论摘要给用户确认结构方向，重大取舍才问）→ Validate（Step 5 命令验证 + 链接检查 + Step 6 收尾清单）→ Handoff（输出 README 全文 + 改动说明）。

## 验证闭环

- **V1 成功判定**：输出通过 CHECKLIST.md 全部项 + Step 6 收尾清单完整。
- **V2 自检标准**：skill-workshop 的 `skill_cli.py validate` + `checklist` 返回 PASS（本技能无本地 Python 脚本，I2 申报设计内）。
- **V3 产出检查**：README 内每条命令 / 路径可追溯到来源文件；双语互链存在；无编造徽章。
- **V4 评估测试集**：正面集——"给这个仓库写个 README""优化我的项目 README""分析这个项目并生成说明文档"；负面集——"写篇公众号文章介绍我的项目""生成完整 API 文档""把 README 翻译成日语"。
- **V5 评估断言**：以下可机器判定——validate / checklist PASS；命令与清单文件字面一致（抽查）；收尾清单含事实来源 / 推断 / 待确认 / 不做项四段；无未标注的 [推测] / [需核实] 宣称。
