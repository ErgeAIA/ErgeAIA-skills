# zuiti 版本历史

## v0.3.5 (2026-08-31)
- 性能审查 + 优化 `scripts/validate_skill.py`（用户 @python-performance-optimization 触发）：**先量化再动手**，用 cProfile + 文件读取插桩 + 子进程墙钟测量定位，不靠猜测。
- 量化结论（诚实口径）：本脚本**没有真实性能问题**——墙钟 261ms/次中，`python -c pass` 空跑基线已占 ~248ms（本沙箱进程创建 + `site`/`sitecustomize` ~93ms 环境开销），脚本自身 `verify()` 实测仅 **0.55ms（占墙钟 0.2%）**；任何对 verify() 的优化在墙钟上都不可能被感知。
- 但插桩暴露一个**真实缺陷**：每个抽屉文件被读取并解析 **2 次**（单次 verify 共 5 次 open，而非必要的 3 次）——v0.3.4 的 O11 `check_drawer_duplicates` 在 [核验]/来源 检查之后又重读重解析了一遍两个抽屉；cProfile 显示它占 verify() 自身耗时的 **~47%**。
- 修复（单遍化）：合并为 `_check_drawer()` 单遍校验——一次 open、一次行循环内同时完成 `[核验]` + `来源/出处` + `抽屉内同文重复` 三项检查；正则 `_QUOTE_RE`/`_PUNCT_RE` 提到模块级预编译（省每行 re 缓存查找）；改为惰性迭代文件句柄（内存 O(最长行) 而非 O(文件)）。
- 实测收益（隔离 in-process 测量，非墙钟）：文件 open **5→3 次/运行**、verify() **0.55→0.41ms（−25%）**、总函数调用 **362,701→240,301（−34%）**。
- 选型留痕：`read_text().splitlines()` vs 惰性迭代实测 0.2274 vs 0.2205 ms（噪声内持平），**选惰性迭代**——同速但内存随文件增长更优。
- 明确不做：`import argparse` 虽在单次 isolated 测量中显示 ~13.9ms 累计，但重复测量被环境噪声淹没（同一组三次测量自相矛盾），且换手写 argv 会丢 `--help`/参数校验，**收益不可靠、UX 有损，故保留 argparse**——遵守「不过早优化」。
- 回归验证：12 条用例全通过（缺 [核验] / 缺 来源·出处 / 两屉各自同文重复 / 缺抽屉文件 / SKILL.md 缺格局·残留 TODO·缺失 / 干净仓 exit0），并**专门验证「跨抽屉复用同句应放行」仍 exit0**（去重仅限单文件内，属设计意图）。
- 三处版本同步 metadata/VERSION/根README/zuiti/README 均 v0.3.5；validate_skill.py exit0；A2/A3/D10/三层禁区安全语义零变更。
